# 角色扮演（Her）架构设计 v2

状态：**草案，待确认**。「待确认」是需要你决定的事；「我的判断」是为推进做的假设。
本版取代 v1。对话链路全部重新设计，**不复用**现有 `/chat/stream.json` 与 `nage`/chat 接口。

## 1. 决定与目标

已确认的决定（来自用户）：

| # | 决定 |
|---|---|
| 1 | 角色扮演整体架构全新设计，不复用现有对话接口与链路 |
| 2 | 记忆建在 agent 层；agent 架构必须支持 memory 与个人重要信息提取 |
| 3 | 渲染器接口抽象，2D 先用 Live2D；**用户用手指拖动 2D 人物是重点功能** |
| 4 | DeerFlow 只负责生成内容；语音（TTS + LiveKit）在外部建一个中间层 |
| 5 | 上架 Google 应用市场（Google Play） |
| 6 | 第一版形态：语音 + 文字，用户可选 |
| 7 | 角色格式按 SillyTavern Character Card V2，支持 V2/V3 导入导出 |
| 8 | 记忆范围：用户维度 |
| 9 | 用户创建角色时的形象和音色：只留扩展点，第一版不做 |
| 10 | 个人记忆不删除（见第 6.4 节的冲突说明） |
| 11 | 官方角色由我们设计 2–3 个（见第 9 节） |
| 12 | 端上 2D 动画人物 + agent（LiveKit + 中间层 TTS + DeerFlow 内容 + memory） |

**非目标（这一版不做）**

- 用户上传任意 Live2D / VRM 模型。
- 服务端视频数字人渲染。
- 3D 形象（留接口，后续用 VRM）。
- 自动跨设备同步的离线对话。

## 2. 总体架构

```
┌──────────────────────── Android 客户端 ────────────────────────┐
│  Compose 外壳（对话 / 角色 / 我的）                              │
│  ├─ 文字输入、文字消息列表                                        │
│  ├─ 语音通话（LiveKit Android SDK：麦克风发布、agent 音轨播放）    │
│  ├─ AvatarRenderer（接口）                                       │
│  │    └─ Live2DRenderer：Cubism Native SDK + GLSurfaceView       │
│  │         · 手指拖动：视线/头/身体跟随（第 5 节）                  │
│  │         · 点击命中区域：发送触摸事件给 agent                     │
│  │         · 嘴型：播放音频振幅驱动                                 │
│  └─ 本地：角色缓存、会话、「我记住的」只读列表                       │
└────────────────────────────────────────────────────────────────┘
          │ LiveKit 房间（音频轨 + 数据通道/文本流）          │ HTTPS（角色、记忆管理）

└───────────────────────────────┬────────────────────────────────┘   └────────────────────────────┘
                                │ 加入房间                                      │
                                ▼                                              │
┌────────────── Companion Agent（Python，LiveKit Agents，Apache-2.0）──────────┴──┐
│  STT（流式） → 提示词组装 → 对话 LLM（流式）→ 句级切分 → TTS（经中间层）→ 音轨    │
│        ▲                 │                                                     │
│        │                 ├─ 工具调用 ─▶ DeerFlow 内容生成（异步，结果回到对话）      │
│        │                 └─ 记忆：检索（回合前） / 提取（回合后，异步）             │
│        │                                  │                                    │
│   触摸事件、情绪事件 ◀─── 形象事件流 ◀─────┘                                      │
└──────────┬──────────────────────────┬───────────────────────────────────────────┘
           ▼                          ▼
┌──── 语音中间层（Voice Gateway）────┐   ┌──── 记忆服务（Memory Service）────┐
│  统一 TTS/ASR 接口                  │   │  MemoryPort 接口 → mem0（推荐）     │
│  Provider 适配器：火山/CosyVoice/…   │   │  按 user_id 隔离；事实/偏好/事件     │
│  流式输出、音色映射、句级缓存、降级   │   │  提取、去重、更新、检索              │
└────────────────────────────────────┘   └───────────────────────────────────┘
           ▲
┌──── DeerFlow 内容服务 ────┐
│  只生成内容（故事、计划、  │
│  资料整理）。不在语音主链  │
│  路上，不直接触达用户声音  │
└──────────────────────────┘
```

**为什么这样分**

- 对话 agent 只有一个，文字和语音走同一条链路，保证同一个角色在两种模式下人设、记忆、情绪完全一致。
- LiveKit 负责实时传输（音频、低延迟数据、文本流）。agent 运行在 LiveKit Agents 框架里，框架自带打断、回合管理、流式 STT/TTS 调度。
- DeerFlow 是多步骤编排框架，延迟高，只能作为 agent 的异步工具。
- 中间层把语音供应商隔离起来，换音色或换供应商不改 agent 和客户端。

## 3. 角色（Character）

角色 = 人设 + 声音 + 形象 + 记忆策略。

```
character
  id, source (OFFICIAL | USER), owner_user_id
  name, tagline, description, tags, avatar_thumb_url
  persona            人设正文（SillyTavern V2 的 description/personality/scenario 合并保存，原始字段另存）
  greetings          开场白列表
  examples           示例对话（最多 3 组参与提示词）
  voice_ref          音色引用，指向中间层的音色 id（第一版只允许平台列表）
  model_ref          形象引用（第一版只允许平台列表；扩展点，见第 8.3 节）
  emotion_map        情绪标签 → 表情/动作
  memory_policy      是否记录用户信息（作者可关闭），默认开
  version, status (DRAFT | PENDING_REVIEW | PUBLISHED | REJECTED | TAKEN_DOWN)
  license            作者声明授权
```

- 角色卡格式：内部字段对齐 V2。导入 V2/V3 JSON 与 PNG（V2 在 `chara` 块，V3 在 `ccv3` 块）；导出 V2 或 V3。V3 的 `emotion` 资源映射到 `emotion_map`；V3 的其它新字段（如 `group_only_greetings`）保留在 `extensions.vvv` 命名空间，导出时原样带回。
- 平台私有字段统一放在 `extensions.vvv`，不混进 V2 顶层。

## 4. 记忆

### 4.1 范围与隔离（决定 8）

- **按用户维度**：记忆的主键是 `user_id`。同一个用户的所有角色共享这份用户记忆（例如名字、职业、喜好只需告诉一次）。
- 每条记忆记录 `source_character_id` 与 `source_message_id`，用户能看到「这条是在和谁聊天时记下的」。
- 不同用户之间完全隔离，服务端在存储层与检索层都强制带 `user_id` 过滤，不依赖应用层约定。
- 作者可以关闭某个角色的记忆写入（`memory_policy=off`），这只影响该角色的写入，不删除用户已有记忆。
- 我的判断（待确认）：跨角色共享用户记忆意味着角色 A 能读到用户在角色 B 里说过的话。这是产品决定，也是隐私敏感点，见第 11 节。

### 4.2 agent 层的记忆流程

```
每回合开始
  └─ retrieve(user_id, 当前话题) → Top-K 记忆 + 最近摘要 → 放进系统提示词的「关于用户」段

每回合结束（异步，不阻塞语音）
  └─ extract(本回合用户消息, 助手回复)
       ├─ 抽取候选：事实（名字、职业、家人）、偏好（喜欢/不喜欢）、重要事件（生日、考试、计划）
       ├─ 打分：重要性 0–1；低于阈值丢弃
       ├─ 去重/合并：与已有记忆比较 → ADD / UPDATE / NOOP
       └─ 写入记忆服务（带 user_id、source_character_id、时间）
```

- 提取由 agent 自己触发（不是由 DeerFlow 触发）。提取用的模型与对话模型可以不同，便宜模型即可。
- 「个人重要信息」的判断标准写进提取提示词，并有一份**禁止提取**清单：身份证号、银行卡、密码、精确住址、健康诊断等敏感类别默认不存；用户明确要求记住的除外，但仍过敏感词检测。
- 用户能在「我的 → 我记住的」里查看、编辑；删除单条是可以的（见第 4.4 节）。

### 4.3 记忆服务选型（决定 2 的核心）

候选项目（均已核实许可）：

| 项目 | 许可 | 按用户隔离 | 个人事实自动提取 | 自托管 | 适配度 |
|---|---|---|---|---|---|
| **mem0**（mem0ai/mem0，约 68.5k star） | Apache-2.0 | ✅ `user_id` 过滤（`agent_id`/`run_id` 也有） | ✅ 单轮 LLM 抽取，ADD-only 积累，Docker 一键部署 | ✅ | **推荐** |
| **Graphiti / Zep**（getzep/graphiti） | Apache-2.0 | ⚠️ `group_id` 分组，**无内置鉴权**，多租户隔离要自己做 | ✅ 从「事件」抽取实体与关系，带时间有效期 | ✅，需要 Neo4j/FalkorDB | 适合 P5 升级：需要时间线和关系推理时再上 |
| **DeerFlow DeerMem**（本地仓库 `agents/memory`） | MIT | ✅ 按 `(agent_name, user_id)` 分桶，有防抖与去重 | ✅ 事实与摘要 | ✅ | 与 DeerFlow 运行时绑定；我们的对话 agent 是 LiveKit Agents，不是 DeerFlow，直接用会把两者耦合。可借鉴其分桶与防抖设计 |
| **TencentDB Agent Memory**（本地仓库） | MIT | ✅ 用户/团队 ACL | ✅ 分层 L0 对话→L1 原子事实→L2 场景→L3 人设画像 | ✅（Node 包） | 分层思想值得借鉴（L3 人设画像正适合「关于用户」段）；生态偏 IDE 与团队场景，不推荐直接用 |
| **ReMe**（本地仓库，agentscope-ai） | Apache-2.0 | ⚠️ 本地优先的文件型记忆，偏个人知识库 | ✅ | ✅ | 文件即记忆，便于用户查看编辑；多用户服务端需要自己做 |
| **Letta**（letta-ai/letta，Apache-2.0） | Apache-2.0 | ⚠️ 一个用户一个 agent 的模型，成本与运维重 | 文档未明确 | ✅ | 不推荐：我们的 agent 是 LiveKit 进程，不适合每用户一个长驻 agent |
| agentmemory、letta-code | Apache-2.0 | — | — | — | 面向编程 agent，不适合 |

**推荐：mem0 作为记忆后端，通过我们自己的 `MemoryPort` 接口接入。**

理由：按 `user_id` 隔离、个人事实提取是它的核心场景、Apache-2.0、可自托管、社区最大、接口简单。`MemoryPort` 让我们以后可以换成 Graphiti（需要时间线时）而不改 agent。

**需要做的验证（P1 前，一周内）**：用 50 段模拟对话测抽取准确率、误提取率、去重效果，以及在敏感类别上的拒绝效果；同时测 mem0 在中文语境下的抽取质量。

### 4.4 删除与保留（决定 10 的冲突）

决定 10 是「个人记忆不删」。但 Google Play 政策要求：用户能在应用内**删除账号及关联数据**，并且要能在应用外申请删除。这两件事有冲突，我的建议：

- **日常：不自动删除**。记忆按用户长期保留，不做时间过期清理。
- **用户主动删除单条**：允许（这是用户的控制权，不是系统删除）。
- **删除账号**：必须能删除该用户的全部记忆。这是 Google Play 和隐私法规的硬要求，不能保留。这条需要你确认，如果坚持「不删」，上架 Google Play 会有审核风险。

### 4.5 DeerFlow 与记忆的关系

DeerFlow 生成的内容（如它替用户写的计划）作为**内容**存在，不自动变成用户的个人事实。只有用户在对话中表达的信息才进入记忆。避免把模型生成的内容当成用户事实。

## 5. 2D 人物：渲染与手指拖动（重点）

### 5.1 渲染器接口（决定 3）

```kotlin
interface AvatarRenderer {
    fun bind(view: AvatarView, spec: AvatarSpec)          // 加载模型，spec 含资源、版本、映射
    fun onEvent(event: AvatarEvent)                       // 情绪、动作、状态（来自 agent）
    fun setMouthOpenness(value: Float)                    // 音频振幅，0..1
    fun onTouch(event: AvatarTouch): TouchResult          // 手指事件（本地处理）
    fun release()
}
```

- `AvatarSpec` 只描述资源（路径、版本、参数范围覆盖、命中区域映射），不含业务逻辑。
- 2D 实现：`Live2DRenderer`，基于 Cubism Native SDK，通过 JNI 封装，渲染在 `GLSurfaceView`。
- 3D 预留：`VrmRenderer`（glTF），同一接口，后续实现。

### 5.2 手指拖动的行为设计

目标：用户手指在人物上拖动，人物的视线、头部、身体跟随手指方向。

**拖动映射**（参数来自 Cubism 标准参数列表）：

| 参数 | 含义 | 标准范围 | 映射 |
|---|---|---|---|
| `ParamEyeBallX` / `ParamEyeBallY` | 眼球方向 | -1..1 | 手指相对中心的偏移，线性映射，权重 1.0 |
| `ParamAngleX` / `ParamAngleY` | 头部左右/上下 | -30..30 | 同上，权重 0.6（头比眼睛慢） |
| `ParamBodyAngleX` | 身体左右 | -10..10 | 权重 0.3，拖动幅度大时才明显 |
| `ParamAngleZ` | 头部歪斜 | -30..30 | 拖动速度快时加一点（撒娇感），权重 0.2 |

- **归一化**：以人物包围盒中心为原点，手指偏移除以半径得到 -1..1，再乘以每个参数的权重和范围。**每个参数都要单独限幅**，不能直接用手指像素值。
- **平滑**：每帧做指数平滑（阻尼），松手后参数回到中性值，回弹时间约 0.4 秒。
- **与动画的关系**：拖动时暂停 agent 下发的「视线」类动作，只保留情绪与嘴型；松手 0.5 秒后恢复。这是我的判断，需要在设备上调参。
- 社区参考：`CubismViewerGems` 等工具的「视线跟随指针」就是对 `ParamAngleX/Y`、`ParamEyeBallX/Y`、`ParamBodyAngleX/Y/Z` 做类似映射，证实这套参数组合可用（来源：[DenchiSoft/CubismViewerGems](https://github.com/DenchiSoft/CubismViewerGems)）。参数的标准范围见 [Live2D 标准参数列表](https://docs.live2d.com/en/cubism-editor-manual/standard-parameter-list/)。

**点击与命中区域**（待验证）：

- 模型的 `HitArea` 命名（如 `HitAreaHead`、`HitAreaBody`）用来判断点在哪个部位。这些名字来自模型配置。
- 点击某部位：本地播放一个短反应动作（不等 agent），同时把 `{type:"touch", area:"head"}` 作为上下文事件发给 agent。agent 可以在下一句回复里自然地回应（例如「别摸我的头啦」）。
- **注意**：Cubism SDK 的命中测试与动作触发样例我没有找到，需要查阅 SDK 的 Web 或 Native 示例代码确认 API（待确认）。

**性能与交互细节**

- 拖动与语音同时发生时，嘴型优先于视线。
- 手指离开屏幕后不立即回弹，由阻尼曲线决定，避免闪动。
- 角色不挡住字幕与输入框：人物区域在屏幕上半部分固定，聊天列表叠在下半部分。

### 5.3 情绪与动作

- agent 的回复里允许输出情绪标签（如 `[joy]`），由 agent 解析并剥离，只把事件发给客户端。标签不进入文字消息。
- 事件通过 LiveKit 数据通道发送（可靠、有序）。格式：

```json
{"v":1,"type":"emotion","turn":"t1","t_ms":1200,"emotion":"joy","intensity":0.8}
{"v":1,"type":"state","turn":"t1","state":"speaking|listening|thinking|idle"}
{"v":1,"type":"touch","area":"head"}           // 客户端 → agent
```

- `t_ms` 相对于本段 TTS 起点，客户端按音频播放进度调度。
- 嘴型不靠服务端发，客户端从播放的音频取 RMS（平滑）驱动。

## 6. 语音：中间层与 LiveKit

### 6.1 中间层（Voice Gateway，决定 4）

职责：把语音供应商隔离起来。

```
VoiceGateway
  ├─ tts.stream(text_stream, voice_ref) → audio_stream        // 流式，句级切分在 agent 侧
  ├─ asr.stream(audio_stream) → text_stream                   // 流式识别
  ├─ 音色映射：voice_ref → 供应商的音色 id 与参数
  ├─ 供应商适配器：火山引擎、阿里 CosyVoice、MiniMax、Azure（候选，待选型）
  ├─ 降级：主供应商失败切备用；记录失败率
  └─ 缓存：同一角色的固定问候语等短句缓存音频，降低成本
```

- 对 agent 暴露一个 LiveKit 的 TTS/STT 插件接口（LiveKit Agents 支持自定义插件），agent 代码不关心供应商。
- 中间层单独部署，可独立扩缩容，和 agent 进程分开。
- 音色授权：平台音色由我们确认授权；不做语音克隆（决定 9 的延伸）。

### 6.2 LiveKit 与 agent

- **LiveKit 房间**：每次会话一个房间。文字会话也开房间（只用文本流，不发音频），保证文字和语音走同一个 agent 进程。
- **agent 进程**：Python，LiveKit Agents（Apache-2.0）。一个房间一个 agent worker，启动时加载角色配置与用户记忆。
- **回合管理**：用 LiveKit 的语音活动检测与回合检测，用户开口即打断播放（用户可开关打断）。
- **文字模式**：客户端通过文本流发送消息，agent 用同样的对话 LLM 回复，回复只走文本流，不合成语音。
- **语音模式**：客户端发布麦克风音轨，agent 回复走 TTS 中间层，音频走 agent 的音轨发布。
- 用户可以在会话中切换模式（文字 ↔ 语音），切换不断开房间。

### 6.3 对话 LLM 与 DeerFlow

- 对话 LLM 直接在 agent 里调用，目标是低延迟（首字节 < 1 秒，是目标不是承诺，需压测）。
- DeerFlow 作为异步工具：agent 判断用户请求需要生成内容（「帮我写一个睡前故事」「帮我把这周的计划排一下」），调用 DeerFlow，立即回复「我去写一下，稍等」，DeerFlow 完成后结果以新消息回到会话，并由 agent 用角色口吻朗读。
- DeerFlow 的输出不直接进入 TTS：先经过 agent 的角色化改写，再进入语音链路。

### 6.4 提示词组装

```
[1] 平台安全策略（最高，不可覆盖）
[2] 角色人设：persona + 开场白风格 + 示例（≤3 组）
[3] 关于用户：Top-K 记忆 + 最近摘要（≤ N token）
[4] 运行上下文：当前模式（文字/语音）、时间、最近的触摸事件
[5] 对话历史：最近 N 轮原文，超出部分用摘要
```

- 语音模式下，回复要短、口语化，并禁止输出 Markdown 与代码块；文字模式允许 Markdown。
- 人设压缩规则同 v1：单段上限 1500 字符，发布时生成压缩版。

## 7. 客户端界面（第一版）

- **底部**：对话、角色、我的。
- **对话页**：顶部是 2D 人物（可拖动），下方是消息列表和输入框。顶部有「文字 / 语音」切换。
- **语音通话**：同一页面，麦克风按钮开启语音；人物状态跟随事件流。
- **角色页**：官方角色列表、角色详情（简介、开场白预览、开始对话）。用户角色入口保留（第一版只能用官方角色做对话，用户角色只做文字人设）。
- **我的**：账号、我记住的（查看/编辑/删除单条）、删除账号。
- **设置**：默认对话模式、语音打断开关、音量。

## 8. 扩展点与第一版不做的事

### 8.1 用户创建角色的形象和音色（决定 9）

- 数据模型已有 `voice_ref` 与 `model_ref` 字段，第一版只允许填平台列表里的值。
- 服务端接口预留 `GET /voices`、`GET /models` 的分页与筛选参数，用户创建角色时选择器接入这些接口即可。
- 不做：用户上传模型、语音克隆、音色训练。

### 8.2 形象扩展

- `AvatarRenderer` 接口即扩展点。增加 3D：实现 `VrmRenderer`。增加新的 2D 模型：只需新增 `AvatarSpec` 资源。

### 8.3 其它扩展

- 记忆后端：`MemoryPort` 可换成 Graphiti。
- 语音供应商：中间层新增适配器。

## 12. 分期

| 阶段 | 内容 | 不需要设备的验收 |
|---|---|---|
| **P0 基础** | 角色数据模型与 V2 导入导出；3 个官方角色种子；中间层接口与一个 TTS 适配器；LiveKit 房间与最小 agent（文字） | 导入导出往返测试；中间层接口的单测（用 fake 供应商）；agent 回合测试 |
| **P1 文字 + 记忆** | 提示词组装；mem0 接入（MemoryPort）；回合后提取；「我记住的」列表；用户维度隔离 | 提取质量验证（50 段对话）；隔离测试（不同用户互不可见）；敏感类别拒绝测试 |
| **P2 语音** | STT 与 TTS 中间层接通；语音回合与打断；文字/语音切换 | 回合状态机单测；音频在设备上验证 |
| **P3 2D 形象** | Live2DRenderer；嘴型驱动；情绪事件；**手指拖动**（第 5.2 节）；命中区域反应 | 映射与限幅的单测；拖动手感与性能需要设备验证 |
| **P4 DeerFlow 内容** | 异步工具调用；结果回到会话并朗读 | 工具调用的超时与失败处理测试 |
| **P5 角色广场** | 用户角色、审核、举报、屏蔽、fork；音色与形象选择器（扩展点） | 状态机与审核队列测试 |

顺序理由：P1 不依赖授权与硬件，能最快让角色「能聊天、会记住人」。P3 卡在 Live2D 授权和设备调参上。
