# 角色扮演（Her）架构设计 v4

状态：**架构重写**。v3 以对话为中心；本版以 **agent 运行时**为中心，对话只是它的一个入口。
本版取代 v3，保留 v3 已确认的产品决定（见第 2 节）。

## 1. 目标：我们要做的是什么

不是「一个能聊天的角色」，是**每个用户自己的 her**：

- **懂这个人**。知道他是谁、在意什么、什么时候会难过、下周三有什么面试。
- **有存在感**。不是等人开口，会在他沉默、在他重要节点、在他需要的时候主动出现。
- **能替他做事**。不只是说「我建议你」，而是能查、能记、能提醒、能打电话，能在授权范围内真的动手。
- **始终是同一个「人」**。文字里、语音里、主动推送里，人设、记忆、语气一致。

这三条决定了架构：**对话不能是中心，agent 才是**。

## 3. 核心架构

```
┌─ 触发层 ────────────────────────────────────────────────────────┐
│ 用户消息 · 定时器 · 事件到期 · 外部 webhook · 系统信号             │
└───────────────────────────┬────────────────────────────────────┘
                            ▼
┌─ 会话层 ────────────────────────────────────────────────────────┐
│ 线程、上下文窗口、回合状态机、打断                                 │
└───────────────────────────┬────────────────────────────────────┘
                            ▼
┌─ 中间件链（固定顺序，可开关）─────────────────────────────────────┐
│ ① 安全 ② 记忆召回 ③ 事件抽取 ④ 人设一致性 ⑤ 工具授权 ⑥ 成本 ⑦ 观测 │
└───────────────────────────┬────────────────────────────────────┘
                            ▼
┌─ Agent 核心（DeerFlow）─────────────────────────────────────────┐
│ 规划 · 多步 · 子 agent · 工具调用 · 上下文压缩                    │
└───────────────────────────┬────────────────────────────────────┘
                            ▼
┌─ 能力层 ────────────────────────────────────────────────────────┐
│ Skill（怎么做） · Tool（能做什么） · MCP（连什么）                │
└───────────────────────────┬────────────────────────────────────┘
                            ▼
┌─ 记忆层 ────────────────────────────────────────────────────────┐
│ 事实记忆（mem0） · 事件时间线 · 会话工作记忆                      │
└───────────────────────────┬────────────────────────────────────┘
                            ▼
┌─ 输出层 ────────────────────────────────────────────────────────┐
│ 文字流 · 语音（TTS/LiveKit） · 主动推送 · 电话 · 形象指令          │
└─────────────────────────────────────────────────────────────────┘
```

**为什么这样分**

- **入口与能力解耦**：同一套 agent，用户主动说话是一条路径，定时器触发是另一条，动作执行是第三条。加一个新入口不用改 agent。
- **中间件显式化**：安全、记忆、授权这些横切关注点如果散落在 agent 里，迟早会漏。固定链 + 固定顺序，漏了是 bug，不是设计。
- **能力分三样**：skill 是「怎么做」（方法论），tool 是「能做什么」（动作），MCP 是「连什么」（外部系统）。混在一起会导致提示词膨胀和行为不可控。
- **记忆分三层**：事实是「他是谁」，事件是「他什么时候会发生什么」，工作记忆是「这次聊到哪」。三者的读法、生命周期、删除语义都不同。

## 4. 触发层

一次交互的起点不止「用户发消息」。

```python
@dataclass(frozen=True)
class Trigger:
    kind: TriggerKind          # USER_MESSAGE | SCHEDULE | EVENT_DUE | WEBHOOK | SYSTEM
    user_id: str
    character_id: str
    payload: dict              # 消息文本、事件 id、信号内容
    origin: str                # 哪个来源触发的，用于审计
```

| 触发 | 场景 | 是否主动 |
|---|---|---|
| `USER_MESSAGE` | 用户发文字或说话 | 否 |
| `SCHEDULE` | 每天早上的问候、每周复盘 | 是 |
| `EVENT_DUE` | 面试前一小时、生日当天、纪念日 | 是 |
| `WEBHOOK` | 外部系统：日历、健康数据、订单 | 视配置 |
| `SYSTEM` | 服务端维护性检查、记忆整理 | 否 |

所有触发都归一成 `Trigger`，再进入同一条管线。**主动发起的特殊之处只在输出通道**（推送或电话），不在 agent。

## 5. 会话层

- **线程**：`(user_id, character_id)` 一条长期线程，跨设备、跨模式。文字和语音共用，保证人设一致。
- **工作记忆**：最近 N 轮原文 + 摘要；超长时由 DeerFlow 的压缩能力处理。
- **回合状态机**：`idle → listening → thinking → speaking → idle`，打断从任意态回到 `listening`。
- **主动回合**：由触发器发起，没有用户消息，上下文是「事件 + 用户近况」，产出通常更短。

## 6. Agent 核心

DeerFlow 作为主脑，接管规划、多步推理、工具调用、子 agent、上下文压缩。

companion 侧只做三件事：

1. 把 `Trigger` 转成 `TurnRequest`（含系统提示词、上下文、可用工具）；
2. 消费 DeerFlow 的流式输出，断句、剥标签、发形象指令；
3. 把回合结束的信号交给中间件（事件抽取、记忆写入、主动性评估）。

**不用 DeerFlow 的能力做对话主脑的理由**：单轮直连模型快，但「her」需要多步——查一下用户说的那个地方天气、看一眼日历再决定怎么回、记住刚才提到的事件。这些都是 DeerFlow 的强项，延迟代价见第 14 节。

## 7. 能力层

### 7.1 Skill —— 怎么做

沿用 job-come 的包格式：`skills/public/<id>/SKILL.md` + `references/*.md`，**由宿主组装进系统提示词**，不依赖模型读文件（job-come 踩过这个坑）。

skill 描述的是**方法论**：怎么诊断、怎么给建议、什么话不能说。不是动作。

新增一个能力时先问：这是「怎么做」还是「能做什么」？是前者写 skill，后者注册 tool。

### 7.2 Tool —— 能做什么

```python
@dataclass(frozen=True)
class ActionSpec:
    name: str                     # remember_event / send_reminder / place_call
    description: str              # 给模型看的，写清楚什么时候用
    parameters: dict              # JSON Schema
    permission: Permission        # READ | CONFIRM | AUTO
    idempotent: bool
    undoable: bool
```

工具是 her 的「手」。没有工具，她只能建议；有了工具，她能替用户做事。

第一批工具（按价值排序）：

| 工具 | 用途 | 权限 |
|---|---|---|
| `remember_event` | 记下时间点事件（面试、生日、复诊） | `AUTO`（只写自己的库） |
| `recall_events` | 查用户近期与相关事件 | `READ` |
| `recall_facts` | 查用户事实记忆 | `READ` |
| `send_message_later` | 在指定时间主动发一条 | `CONFIRM` |
| `place_call` | 主动发起语音通话 | `CONFIRM` |
| `read_calendar` | 读日历（接入后） | `READ` |
| `create_reminder` | 建系统提醒（接入后） | `CONFIRM` |

### 7.3 MCP —— 连什么

LiveKit Agents 自带 MCP 客户端（SSE / streamable HTTP），按需把外部系统挂成 toolset。

- 记忆、角色这些内部能力**走进程内接口**，不绕 MCP。多一跳只会加延迟。
- 外部系统（日历、邮件、健康数据）走 MCP，因为它们的鉴权、配额、可用性都不由我们控制。
- 工具过多时用 `tool_search` 按需挂载，避免提示词膨胀。
- **不开放文件读写类工具**给模型。

## 8. 中间件链

固定顺序，每一环都可单独开关与测试。顺序不是随意的：安全必须最先，成本必须最后（它要看到前面所有环节的用量）。

```python
async def chain(ctx: TurnContext, next_mw) -> TurnResult:
    ...
```

| # | 中间件 | 作用 | 失败时 |
|---|---|---|---|
| ① | 安全 | 平台策略、注入防护、未成年人保护 | 拒绝，不降级 |
| ② | 记忆召回 | 事实 + 事件 → 「关于用户」段 | 记日志，继续（记忆是增强） |
| ③ | 事件抽取 | 回合后异步抽取事件与事实 | 记日志，重试 |
| ④ | 人设一致性 | 检查回复是否偏离人设与语言 | 记日志，不阻断 |
| ⑤ | 工具授权 | 按 `ActionSpec.permission` 拦截或要求确认 | 拒绝该动作，回合继续 |
| ⑥ | 成本 | 每用户/每回合预算 | 截断或拒绝 |
| ⑦ | 观测 | 日志、耗时、用量、Langfuse | 不影响主流程 |

**为什么抽取放在中间件里而不是 agent 里**：抽取要在每回合后必然发生，靠模型「记得去做」是不可靠的。

## 9. 记忆：三层

### 9.1 事实记忆（mem0）

用户是谁：名字、职业、偏好、家人、反复出现的困扰。

- 按 `user_id` 隔离，跨角色可读，每条带 `source_character_id`。
- 回合前召回 Top-K，回合后异步抽取。
- 禁止类别：身份证号、银行卡、密码、精确住址、医疗诊断。

### 9.2 事件时间线

用户什么时候会发生什么。

```python
@dataclass
class TimelineEvent:
    id: str
    user_id: str
    kind: EventKind            # INTERVIEW | BIRTHDAY | EXAM | APPOINTMENT | ANNIVERSARY | OTHER
    title: str
    at: datetime               # 发生时间
    recurrence: str | None     # 每年/每月，为空表示一次性
    source_character_id: str
    source_message_id: str
    confidence: float          # 抽取置信度，低于阈值只存不驱动主动
    status: EventStatus        # SCHEDULED | DONE | CANCELLED | MISSED
    remind_before: timedelta | None
```

**为什么和事实记忆分开**：

- 事实是「用户喜欢安静」——长期有效，按语义检索。
- 事件是「下周三下午两点面试」——有时间锚点，按时间窗口查询，会过期，会被取消。
- 用同一个存储会让两种查询互相拖累，也让删除语义含糊。

事件的两个消费者：**对话时提供上下文**（「你面试准备得怎么样」），**主动性时提供触发**（面试前一小时提醒）。

### 9.3 工作记忆

当前会话的最近上下文与摘要。不进长期存储，会话结束即释放。

### 9.4 删除语义

| 场景 | 事实 | 事件 | 工作 |
|---|---|---|---|
| 用户删单条 | 删除 | 删除 | — |
| 账号删除 | 全删 | 全删 | 释放 |
| 事件到期 | — | 标记 `DONE`/`MISSED`，保留用于回顾 | — |

## 10. 主动性

这是「her」和「聊天机器人」的分界线，所以它是独立子系统，不是对话里的 if 分支。

```
定时扫描（每 5 分钟）
   ├─ 取出该窗口内事件到期的事件
   ├─ 取出沉默超过阈值的用户
   ├─ 取出周期性问候（早安、周末复盘）
   ▼
InitiativePolicy 判断要不要开口
   ├─ 安静时段？（用户作息）
   ├─ 最近打扰过？（频控：每天 ≤ N 次，每周 ≤ M 次）
   ├─ 用户是否关闭了主动？
   ├─ 这件事值不值得打扰？（重要度评分）
   ▼
组装主动回合（Trigger.Kind = EVENT_DUE / SCHEDULE）
   ▼
输出通道：应用内消息 / 推送 / 电话（用户可分别关闭）
```

**必须有的约束**

- **频控**：默认每天最多 2 次，每周最多 6 次，用户可调。
- **安静时段**：默认 23:00–08:00 不发，紧急事件除外（且紧急的定义要很窄）。
- **可退订**：主动消息里有明确关闭入口，关闭后不再发。
- **可解释**：「我为什么给你发这条」——用户在设置里能看到触发原因。
- **失败不重试堆积**：推送失败不补发，避免用户回来看到一串。

## 11. 动作与授权

her 能做事，就必须有授权模型。

| 级别 | 含义 | 例子 |
|---|---|---|
| `READ` | 只读，无需确认 | 查日历、查记忆 |
| `CONFIRM` | 需要用户同意才执行 | 发提醒、打电话、写日历 |
| `AUTO` | 自动执行，事后告知 | 记事件、写自己的记忆 |

- **确认的形态**：文字模式下是一条需要点确认的消息；语音模式下是一句追问（「要我帮你记下周三的面试吗？」）。
- **审计**：每个动作记 `ActionLog{who, what, args_hash, result, at}`，用户能查。
- **可撤销**：能撤销的动作提供撤销入口；不能撤销的（打电话）必须在 `CONFIRM` 级别。
- **不给模型自主扩权**：模型不能把自己的工具权限改高，权限来自配置。

## 12. 形象指令

形象由**结构化指令**驱动，不靠解析文本。

```python
sealed interface AvatarCommand {
    SetState(state)          // idle | listening | thinking | speaking
    Emotion(name)
    Mouth(openness)
    Gaze(x, y)               // P3b
    Gesture(id)              // P3b
    LookAt(target)           // P3b
    Speak(segment, emotion)  // 带情绪的整句，供未来骨架用
}
```

agent 的输出里，情绪与动作作为**结构化字段**（`[joy]` 这类标签在 agent 侧剥离并转成指令），不进入显示文本。

渲染器声明能力，不支持就忽略——这样 v1 只需实现三个，P3b 换 Spine 时补齐即可。

## 13. 语音

- 供应商走策略模式，第一版火山引擎；换供应商只改适配器与角色的 `voice_ref`。
- 流式合成，按句断句；不支持流式的供应商退化为按句合成。
- 用户开口即打断（可关），打断要真的取消 DeerFlow 回合，避免后台继续烧 token。
- **主动电话**复用同一条链路：服务端发起，客户端收到来电界面，接起后进同一个房间。

## 14. 延迟与成本

- 首包目标 < 1.5 秒（DeerFlow 比直连慢，这是为能力付的价）。超过 2 秒时，短回复改走直连模型的分支——**先压测，再决定是否要这个分支**。
- 每用户每回合预算由中间件 ⑥ 控制。
- 抽取、主动性评估用便宜模型，与对话模型分开。
- 单次主动推送的成本要记在用户维度，避免频繁打扰同时烧钱。

## 15. 参考项目与本设计的取舍

| 项目 | 借鉴 | 不照搬 |
|---|---|---|
| **OpenMausBot** | 每个 bot 独立配置：模型、指令、工作目录、可操作环境 | 桌面多 agent 工作台形态不适合移动端产品 |
| **Rakazo** | 持久 agent；routine 用 Markdown 表达；**行动前要人工批准** | 它是「AI 同事」而非陪伴，语气与场景不同 |
| **OpenMuse** | agent 有自己的执行环境；长任务可见、可等待 | 生产力助手定位，没有情感与主动性 |
| **ChatWaifu_Mobile** | 端上 Live2D + 唇形、端上 TTS 的思路；2D 人物是产品核心 | 模型禁止商用；我们用自研分层素材 |

**Rakazo 的「行动前批准」验证了第 11 节的授权分级**：一个能替用户做事的 agent，如果没有确认与审计，用户不敢用。

## 16. 数据与隐私

- 记忆、事件、动作日志都属于用户，可导出、可删除。
- 账号删除：全部删除（事实、事件、工作记忆、动作日志、会话）。
- 主动推送涉及「未经请求的通信」，Google Play 对通知与营销有单独要求：必须是服务性消息，必须有退订。
- 语音、事件时间线属于敏感数据，隐私政策要逐项声明。

## 17. 分期

| 阶段 | 内容 | 验收 |
|---|---|---|
| P0 骨架 | 触发层、会话层、中间件链、DeerFlow 接入、两个角色与 skill、会话接口 | 触发归一化、中间件顺序、回合端到端 |
| P1 记忆 | 事实记忆（mem0）、事件抽取与时间线、`recall_*` 工具 | 抽取准确率、隔离、删除零残留 |
| P2 语音 | 火山 TTS/ASR、打断取消、文字语音切换 | 回合状态机、取消传播 |
| P3 形象 | 指令框架、简单渲染器 | 指令映射、设备观感 |
| P4 主动性 | 调度器、策略、频控、推送通道 | 频控与安静时段、退订生效 |
| P5 动作 | 授权分级、确认流程、审计、第一批工具 | 授权拦截、审计完整、撤销 |
| P6 电话与扩展 | 主动来电、MCP 外部系统、Spine | 来电链路、工具授权 |

顺序理由：P0 定住骨架；P1 让「她记得」成立；P4/P5 才是「her」的分水岭，但必须建立在稳定的记忆与授权之上。

## 18. 待确认

1. **主动性默认强度**：默认开启还是默认关闭、由用户主动打开？（涉及审核与用户观感，我建议默认「重要事件提醒开、日常问候关」。）
2. **主动电话的范围**：任何用户都能被主动打，还是只对显式开启的用户？
3. **事件抽取的模型**：用便宜模型抽取 + 规则校验，还是用一次强模型做高精度？
4. **动作的第一批**：上面列的五个工具是否就是 P5 的范围？
5. **OpenMuse / Rakazo 是否真要参考**：它们都是生产力 agent，与陪伴产品的差距较大，我建议只借鉴「执行环境 + 人工批准」两点。

## 19. 假设（可推翻）

- DeerFlow 的延迟在可接受范围（P0 压测）。
- 事件抽取的准确率足够驱动主动提醒而不误报（P1 验收）。
- LiveKit 支持服务端主动发起通话（P6 验证）。
- 用户能接受「her 会主动找你」，且频控设计足够克制（上线后看数据）。
