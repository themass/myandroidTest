## 0. Module-level picture

`settings.gradle` includes: `:app :common :core :mediaview :speech :imaging :cast :feature-video :feature-chat :feature-photosolve :feature-user :feature-content :feature-companion :dh-engines :retromusic :chatkit :feature-camera-fx`. Module graph is enforced by `ModuleGraphTest`: **features never depend on each other**; `:feature-companion` is deliberately frozen (own branch, old package name `com.openapi.ks.myapp.*`, sole LiveKit holder, deps only `:core` + `:common`). `:feature-camera-fx` is compiled into the app but every entry point is `FLAG_DEBUGGABLE`-gated. `demos/avatar-lab`, `spike/`, `evidence/`, `tools/`, `scripts/` are NOT gradle-included.

So at build level chat-role management (`:feature-chat/roles`) and the Her presentation stack (`:feature-companion` + `:dh-engines` + `:feature-camera-fx`) are already separate modules with no direct edge — the bridge is `:app` routing + server contracts.

## 3. Coupling points (persona ↔ presentation)

1. **character_id → avatar pack binding**: `CompanionScreen.kt` L224-231 `LaunchedEffect(renderer, characterId)` → `AvatarSync.syncFor(characterId)` → `AvatarPackStore.bind(roleId, avatarKey)` in `index.json`. The chat/companion persona id doubles as the avatar-bind key (`GET /v1/avatars?role_id=`). Renderer for the chat screen is hardcoded `SimpleAvatarRenderer` (L143).
2. **character_id → room/session/voice**: `POST /v1/voice/sessions {character_id}` (CompanionApi L99); voice binding is server-side `voice_ref` on the character JSON — switching character switches voice automatically (documented as intentional; client-side character→voice hardcoding is an explicit anti-goal).
3. **Engine choice is a client-local pref, not server data**: `companion.dh_call_stage` in SharedPreferences (DhLabPreferences L23-31) — the presentation engine is decoupled from the persona, but decoupled *into a debug-only local setting*, with no server field. **No server character model carries a `renderer`/engine field.** The proposed server field exists only in `CharacterAssetPack.kt` (`"engine"` L29) and docs.
4. **character list UI already reaches into the pack store**: `CompanionManagementScreens.kt` `CharacterListAvatar` renders from `AvatarPackStore` — presentation asset store consumed by persona UI.
5. **Two character ID universes**: chat text uses Int `characterId` (legacy) + String `roleId` (catalog/agent); companion voice uses String `characterId` ("linche"). `docs/design/2026-11-27-her-character-wardrobe-contract.md` flags building a traceable chat↔companion character ID mapping as step 1. The wardrobe doc's `HerCharacter/HerRelease/HerInstance/HerSession` four-object split is the target contract.
6. **Effects don't reference characters at all today** — they're driven purely by gesture words (`cmp.cue → AvatarEventMapper → AvatarCommand.Gesture → uiState.gestureSeq → StageEffectMapper → LottieFxLayer`). That's the good news: the fx path is already persona-agnostic. The `CameraFxStickerRenderer` typealias + `onCameraStageGesture` callback are the seams.
7. **ATRI special-casing** inside presentation: `Live2dModelChoice.ALLOWED` whitelist (L12), `fullWardrobe = activeModelDir == "ATRI"` (Live2dDigitalHumanEngine L51), `Live2dTouchReaction` enum axes — presentation hardcodes a specific character identity (flagged in the wardrobe contract doc).
8. **Local-only lists with no server backing**: `DefaultAgentRoles` (AgentChatEntry L42-47), `BundledRoleCatalog` (APK asset `personas/agency-agents-import.json`, fallback-only), `LocalRoleCatalog`, `BundledAvatars.ROLE_BINDINGS`, `VOLC_VOICE_NAMES` (CompanionModels L139-142), `DEFAULT_CHARACTER_ID="linche"`, effects whitelist (`FxAssets`), camera sticker whitelist (`StickerAssetIds`), Live2D model whitelist, wave styles/call theme prefs (`companion_wave`), roles favorites/recents, engine pref/watchdog prefs. **fx catalog, sticker catalog, effect options, model catalog: all hardcoded lists.**

## 4. Performance & extension state

- **Effect compositing**: Compose Box sibling overlay (CPU-rendered Lottie via lottie-compose), zero GL involvement, prewarmed compositions, one-at-a-time, 400 ms dedupe, static-frame fallback under reducedMotion, SKIP when stage zoomed. Camera stickers: Compose Canvas/Lottie on top of PreviewView with MediaPipe landmarks → pure-math anchoring (FILL_CENTER + mirrorX). All heavy math is JVM-testable pure functions.
- **Hard constraints**: (a) Live2D native scene changes only via `JniDispatcher` = `GLSurfaceView.queueEvent` (`Live2dRuntime.kt` L85-91, L159-160) — any new wardrobe/asset hot-swap must serialize through the GL queue (`Live2dHotSwap` exists); (b) gesture arbitration lives ONLY in `avatarStageTransform` — no new layer may add `pointerInput`; (c) effects deliberately do not follow the stage pinch transform (fixed viewport anchors); (d) WebView engines (SPINE/TALKING_HEAD/VRM) carry compositing cost, TalkingHead's mpfb.glb is 36.8 MB shipped in assets (docs: must move to AssetStore or be cut); (e) Rive native lib debug-only by policy.
- **How to add an effect today (5 steps, all client-side)**:
  1. Drop Lottie JSON into `feature-companion/src/main/assets/fx/` (and `feature-camera-fx/src/main/assets/fx/` if it should be a camera sticker) — spec: transparent, no expressions, no embedded bitmaps, ≤100 KB (generator: `tools/gen_lottie_fx.py`).
  2. Register in `FxAssets` (StageEffect.kt L47-61: constant + `Spec(assetId, category)`).
  3. Add a word case in `StageEffectMapper.fromGesture` (L30-45) — the gesture word must be in the server `cmp.cue` gesture vocabulary or a local trigger.
  4. Add label + gestureId (+ camera whitelist membership) in `StageFxOptions` (L30-49), and mirror `StickerAssetIds.ALLOWED` in `CameraFxOverlayPolicy.kt` L26-31 if a sticker.
  5. Add/update JVM tests (`StageFxOptionsTest`, `FxAnchors`-side tests) — then rebuild+install from mainline.
- **What a downloadable per-her effect/sticker catalog would need**: replace the three hardcoded whitelists (`FxAssets`, `StickerAssetIds.ALLOWED`, `StageFxOptions.labels/gestureIds`) with a catalog-backed descriptor (assetId, target HER/USER, category, anchor, gestureWord/version, version, sha256, downloadUrl, license), reuse the verified-install machinery (AvatarPackStore/CharacterAssetPackStore patterns — CharacterAssetPack is the right base: per-file sha256, versioned immutable dirs, staging+atomic rename), extend `StageEffect.Play` to carry a pack-resolved source instead of a fixed asset path, extend the cue envelope toward the documented `Cue(schema_version, session_id, turn_id, sequence, intent, duration)` with command-ID dedupe (400 ms window today is per-asset, local), and keep whitelist validation server-catalog-issued so the server never sends arbitrary local paths.

## 6. Verdict for the split

Already clean: module graph (no chat↔companion edge); the cue/event pipeline (`cmp.cue → AvatarEventMapper → AvatarCommand.Gesture`) is engine-agnostic and effect-agnostic (`FxEngineAgnosticTest` guards it); persona data (character JSON, sessions, memory) never touches engines; effects never reference characters.

Not clean / missing for "same lifecycle for both" + downloadable catalog:
1. **No server-owned presentation descriptor**: engine pick is a debug SharedPreferences key (`companion.dh_call_stage`); no `renderer` field on `/v1/characters`; character pack binding goes through a legacy `/v1/avatars?role_id=` illustration-pack endpoint, while the general pack contract (`CharacterAssetPack`) is unwired. HerCharacter/HerRelease/HerInstance/HerSession + personaProfileRef exist only on paper.
2. **Two character-ID universes** (Int characterId / String roleId in chat; String characterId in companion) with no mapping table.
3. **Effect/sticker catalogs are three duplicated hardcoded whitelists** + hardcoded gesture-word mapping; no versioning, no download, no per-her availability, no command-ID dedupe (only a local 400 ms per-asset window).
