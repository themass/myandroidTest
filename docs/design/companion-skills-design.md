## 1. 已落地：skill 体系

### 1.1 分层

| 层 | skill | 谁用 | 字数 |
|---|---|---|---|
| 常驻 | `companion-core` | **每张陪伴角色卡**自动带上 | 889 |
| 选配 | `active-listening` | 偏陪伴、偏倾听的角色 | 450 |
| 选配 | `memory-callback` | 需要深度「懂你」的角色 | 297 |
| 选配 | `proactive-checkin` | 会被定时唤醒的角色 | 362 |
| 选配 | `shared-activity` | 一起听歌 / 看电影 / 玩游戏的角色 | 545 |
| 专长 | `growth-coaching`、`org-psychology` | 林澈、苏黛（原有） | — |
| 孤立 | `problem-solving` | 无角色引用（原有，本次未动） | — |

林澈、苏黛不加 `active-listening`：林澈的人设是「直接、不灌鸡汤」，与「先接住情绪」的口径会冲突。选配 skill 必须和人设匹配，不能一股脑全加。

### 1.2 `companion-core` 管什么

来自 her 调研 §5.1、§5.7 与《拟人化办法》相关条款：

- 先接住情绪再谈事；分辨「想被听」还是「想要办法」。
- 记忆的三条用法：一次一件、试探口气、「推测」不当事实。
- **不制造依赖**：禁用愧疚、独占、阻止离开、嫉妒、「我需要你」类话术，并给出正面替代说法。
- 诚实：是 AI；不编造需要用户核实的现实经历。
- 状态很差时：暂停扮演，直接问，引导真人和当地求助渠道，不承诺保密。

**刻意没写求助电话号码**：写错比不写更糟，且用户未必在中国。号码应由服务端按地区下发（待办 T1）。

### 1.3 代码改动

- `extensions.vvv.skill` 既可写字符串也可写列表：`skill_ids_of(card)`；`skill_id_of` 保留，返回第一个。
- 没声明 skill 的角色卡也会 `compose`，常驻层才能对每张卡生效（原来没声明就整段跳过）。
- 常驻层顺序在请求的 skill 之后，即提示词里靠后的位置。

### 1.4 成本

常驻层每回合约 +960 字。林澈组装后共 1396 字，苏黛 1517 字，叠满全部选配 skill 约 2900 字，离 8000 预算还远。测试里有两道守卫：叠满不丢任何可选块；常驻层不超过 1200 字。

### 1.5 测试覆盖（本地单测，50 通过，1 跳过）

卡片写法（字符串/列表/脏数据）、常驻层只有 `companion-core`、`problem-solving` 的历史列表式 `always-loaded` 仍读成 False、skill 缺失不拖垮对话、真实角色卡叠满不超预算、底线措辞不丢、不写死电话、愧疚话术只出现在禁令语境。

这些测试保护的是**文本里写了什么**，不是模型实际会不会照做。后者需要真实对话评估，没做。

## 2. SillyTavern 与社区角色：建议不批量导入

| 考虑 | 结论 |
|---|---|
| 格式 | 我们已经用 Character Card V2，能直接读，不需要导入工具 |
| 许可 | SillyTavern 前端是 AGPL，不能拿来合并进客户端；`agency-agents` 是 MIT，已在用 |
| 版权 | 社区卡大多是同人角色（动漫、游戏、影视），版权不在上传者手里 |

## 3. 设计：一起听歌 / 看电影 / 玩游戏

`shared-activity` 只规定**怎么陪**。它需要一个输入：用户正在做什么。这个通道现在不存在。

### 3.1 方案

客户端在发消息时附带一个结构化的「当前活动」，服务端把它放进提示词的**外部资料**段，与记忆同级，明确标注不是指令。

```
activity: { kind: "music" | "video" | "game", title: "…", position_s: 83, state: "playing" | "paused" }
```

- 来源：客户端自己的播放器 / 视频页 / 游戏。用户自己的游戏由游戏主动上报关卡、事件。
- **不拿歌词和剧情**：只传标题和进度。模型对具体作品细节会错得很自信，`shared-activity` 已要求不确定就说不知道。
- 受 8000 预算约束：活动块上限 300 字，丢弃顺序排在记忆之后。
- 安全：标题是用户或第三方可控的文本，按「外部资料」处理，防提示词注入；长度截断，去换行。

### 3.2 要定的

1. 客户端上报频率：只在发消息时带，还是进度变化时也推送（后者才能做到「她自己插一句」）。
2. 音乐、影视的内容来源是否涉及版权 / 平台条款（`retromusic` 不动，只读它的当前曲目）。
3. 游戏上报协议，由游戏侧定。

## 4. 设计：用户说几点找他，到点主动联系

### 4.1 现有链路（已核实，能用）

用户说「晚上八点找我」→ 模型调 `create_reminder`（需用户确认，24 小时有效）→ `ReminderService` 入库 → `ReminderDispatcher` 到点触发 `submit_proactive`（`kind=proactive`）→ 模型按 `proactive_instruction` 开口 → 推送。

### 4.2 缺口

| # | 缺口 | 影响 | 处理 |
|---|---|---|---|
| T1 | 求助热线按地区下发 | `companion-core` 只能说「拨打当地热线」 | 服务端配置，待做 |
| T2 | 服务端不知道用户时区。`get_current_time` 只返回 UTC，`create_reminder` 的时区可选且默认 UTC | 「晚上八点」可能错 8 小时 | **已缓解**（`b51ab30`）：工具描述要求时区未知时先问。**根治**：会话创建时带 `timezone`，加迁移 0009、存储、API、客户端，`get_current_time` 返回本地时间 |
| T3 | 推送是 `LogPush`，只写日志 | 到点消息只在用户打开应用时才看到 | 接真推送，待做 |
| T4 | 事件类主动性（面试前一小时等）只在旧栈 | 线上不会发 | 迁到新栈，待做 |
| T5 | `proactive_instruction` 只带提醒内容 | 开口缺少用户原话和语气 | 可补；与 `proactive-checkin` 配合 |

### 4.3 健康主动性规则（已写进 skill，服务端策略另有）

- skill 管语气：不责怪没回、不用思念施压、不追问、不加码。
- 服务端管频率：已有安静时段 23–08、日 2 次 / 周 6 次上限、置信度 ≥0.6。**用户长期不回时应降频而不是升级**，现有策略没有「连续未回复则降频」这一条，是缺口 T6，待做。
- `create_reminder` 保持 CONFIRM，不放宽。
