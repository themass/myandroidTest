# 重点方向路线图（2026-11-24）

## 目标与范围

这份路线图把四个持续投入方向拆成可验收的工作：LiveKit 语音基建、Her 角色与教学展示、摄像头/人体交互与虚拟试衣、图像与视觉模型候选评估。它是规划文件，不代表其中尚未实现的能力已经交付，也不替代 `tasks/plan.md`、`tasks/todo.md` 中正在进行的 Chat/Share/Voice 任务。

路线图服务于一个收口标准：每个 worker 接受边界明确的任务，交付时提供目标、改动、验证证据和未解决阻塞；目标内不留未列明事项。独立的新方向另立任务，不混入已经完成的工作。

## 当前基线与已知边界

### LiveKit

- 自托管拓扑和切换步骤以 `README-livekit.md`（myconf 仓库）为准：信令经 `livekit.ok123find.top:443` 两跳到 104 的回环 7880；媒体 UDP 50000–50019、TURN UDP 3478、TCP fallback 7881 直达 104；worker 同机连回环信令。
- P0.5/P2 协议四项（hello/上麦、静音预缓冲不触发 t0/barge、真实音频后才允许 barge、可听窗打断）已有同 attempt/job 的真机与服务端证据，按已关闭处理。不得把该协议线重新列成开放任务。
- 首帧延迟仍未达标，且出现服务端空回复；已有对账将两类分别归到 TTS/媒体首帧（F16）与 tos 空回复线。需继续独立定位，不能以协议验收通过代替体验验收。
- 任何生产切换都必须先完成蜂窝网络 ICE 冒烟；失败时按 runbook 回滚到原 LiveKit URL/密钥并重启对应进程。禁止 Docker；生产 LiveKit 使用官方二进制与 systemd。

### Her

- 已有 Agent 运行时、角色卡、工具授权、事实/事件/工作记忆等设计；实际服务端存在旧语音栈与新文字栈并行的差异，语音接入真实 agent、记忆共享策略、真实角色素材/音色仍需按当前代码和部署逐项核实。
- 角色扮演 demo 应展示同一角色在文字、语音、事件记忆和结构化形象指令下的一致性；教学输出应能解释角色如何倾听、追问、给建议和守边界，而不只是静态文档。
- 防谄媚、防依赖、未成年人边界、清晰 AI 标识、用户退出与主动消息硬频控属于设计门槛；法规细节及上线前适用性须由法务人工复核，调研文档不是法律意见。

### 摄像头与舞台特效

- 已定架构：用户主动开启相机后才绑定 CameraX；设备内 MediaPipe 输出锚点；相机贴纸/线框是本地叠加层；舞台特效经 `emitStageGesture` / `cmp.cue` 和既有 `LottieFxLayer`，不另造事件总线。
- 相机当前 v1 以人脸锚点与 Pose 骨架为基础；基础 gesture→stage cue 映射已实现。指尖 15–22 未画，HandLandmarker / GestureRecognizer 的手部识别接入、通话内人脸贴纸入口和完整真机观感仍待验收。
- 头部/服装/帽子替换要以 `scripts/dh-lab/live2d-lab-assets/wardrobe-spec.json` 为单一事实源；未有真实素材或验证参数的变体维持 pending，不标 active。摄像头只在用户进入相关功能并授权后启动。
- 用户提到的 `sophiamyang/finger-frame-effect-ai` 是候选参考，不预设其代码或模型可直接集成。

### 图像与模型候选

- IOPaint/LaMa（异物去除）、AnimeGANv3 ONNX（端侧风格化）、手势/帧效果项目先做隔离的可复现评估，再决定是否进入产品集成。
- 准入审查分别覆盖代码许可证、模型权重许可证、训练数据/素材来源、商用与分发条款、隐私/内容风险、Android 设备性能和维护状态；任一关键权利未知时只保留研究结论，不合并依赖或素材。
- Lada 去马赛克排除在主线之外。只有明确正当场景、权利核查和内容审查均通过后，才重新立项。

## 总体顺序与依赖

```text
A. 证据与指标基线
   ├── B. LiveKit 体验性能与可靠性 ───────────┐
   ├── C. Her 角色一致性与教学 demo ─────────┤
   ├── D. 相机交互 / 手势 / 试衣规格 ─────────┤── G. 集成门槛与阶段验收
   └── E. 图像模型与开源候选评估 ─────────────┘
                     D + E 通过后 ── F. 受控原型集成
```

A 是各线共同的入口；B、C、D、E 可以各自推进，不共享代码写入范围。F 只能在 D/E 的评估门槛通过后开始。G 逐阶段核验交付证据、回滚方式和目标内遗留。

## 阶段 A：证据、指标与任务边界

### A1. 建立 LiveKit 体验基线

**产出：** 一份按 attempt/job 配对的基线记录，覆盖连接、握手、ASR、LLM/agent、TTS 首帧、首个可听音频、空回复、打断与会话结束。

**验收：**
- 至少 3 次蜂窝网络会话与同一 attempt/job 的客户端、104 服务端日志关联。
- 每个延迟都注明起止事件、单位、样本数和分位数；空回复单独计数。
- 与已关闭的协议四项分栏，不再把已过线项目混入开放问题。

### A2. 核实 Her 线上真实链路

**产出：** 文字与语音的端到端调用图，标出真实 agent、记忆、角色、人设素材、工具授权、会话锁及推送通道的已实现/缺失状态。

**验收：** 每项状态都引用当前代码、配置或部署证据；设计文档与运行实现不一致时记录为差距，不按设计推定已交付。

### A3. 固定 worker 收口格式

**产出：** 每个子任务使用“目标 / 范围 / 交付 / 验证命令或人工步骤 / 证据位置 / 剩余阻塞”收口；跨方向新发现转独立任务。

**验收：** 协调人能从报告判断目标是否全完成、验证是否执行、目标内是否有遗留；未运行的测试或未做的真机/线上验收明确写未完成。

## 阶段 B：LiveKit 网络、延迟与可靠性

### B1. 首帧延迟分段定位

**依赖：** A1。

拆出握手/房间就绪、用户停说检测、ASR final、agent 首 token、工具等待、TTS 请求和 TTS 首帧、媒体首包及端上播放；对齐 monotonic 时间戳并区分客户端/服务端时钟。优先处理已有证据指出的 TTS 首帧与 tos 延迟，不无证据改 ICE 或 barge 协议。

**验收：** 给出至少 3 次同场景复测的阶段耗时和长尾；每次优化前后用同一组场景比较；首音频 P50/P95 目标由 A1 基线后在子任务中明确，不预填未经产品确认的数字。

### B2. 空回复与失败降级

**依赖：** A1、A2。

沿 `said=''`、interrupted、无 TTS start、provider timeout/error 等状态追到产生空回复的边界，定义用户可听见的失败提示/重试策略和不重复烧费的约束。

**验收：** 注入或复现空内容、超时和 provider 错误时，不出现无解释静默；日志包含 session/job、失败阶段和耗时；重试具备次数上限且不会重复执行外部副作用。

### B3. 自托管网络和部署韧性

**依赖：** A1；部署/生产变更按单独变更窗口执行。

持续检查两跳信令、证书、DNS、UDP 媒体、TURN 3478、TCP 7881、安全组和 systemd 状态；形成上线前蜂窝冒烟、切换、观察、回滚步骤。先在非生产/可控窗口验证，不直接拿线上用户流量做试验。

**验收：** 蜂窝网络完整通话成功并有同场客户端/服务端证据；记录 UDP 与 fallback 路径；回滚步骤实际演练或在隔离环境验证；密钥不进入文档或日志。

### B4. 容量与长会话稳定性

**依赖：** B1、B2。

测并发会话、worker 内存/CPU、连接重建、长会话上下文增长、provider 限流和进程排空；根据测量决定是否调整 worker 数、资源和超时。

**验收：** 报告负载形状、资源曲线、失败率和并发上限；升级/重启后活动通话排空行为有验证；所有调优附回滚值。

## 阶段 C：Her 角色体验、教学与展示

### C1. 选定首个教学场景并定义评分卡

**依赖：** A2。

选一个能展示倾听、澄清、记忆引用、角色边界和结尾行动的短场景；建立人工评分项和不通过样本，避免只展示理想单轮台词。

**验收：** 脚本包含至少正常、含糊输入、情绪化输入、用户纠正记忆、退出/不继续五类路径；评分卡能区分事实正确性、角色一致性、帮助性、谄媚/依赖风险和延迟。

### C2. 交付可运行的角色扮演教学 demo

**依赖：** C1、A2；语音演示需 B2 的可听失败处理。

做可重复启动的 demo，展示同一官方自创角色在文字与语音中的一致行为、事实/事件记忆的来源与纠错、工具需确认时的流程，以及明确 AI 身份和退出入口。演示素材与声音须有自有或可核实授权。

**验收：** 新成员按 README 可运行；演示脚本全路径可重复；角色记忆不跨越授权边界；角色输出不声称是真人、有意识或要求用户持续陪伴；提交屏幕/录屏或日志证据及评分结果。

### C3. 角色质量回归与展示打磨

**依赖：** C1、C2。

建立小型中文回归集，覆盖人格稳定、事实引用、拒绝谄媚、边界和结构化形象指令；展示效果通过现有叠加层和 `cmp.cue` 扩展，不改原 UI 主结构。

**验收：** 每次角色卡、模型或提示词变化运行同一回归集；质量退化可比较；舞台动作可由 cue 追踪，失败不影响对话/音频主链。

## 阶段 D：摄像头、人脸/人体、手势与试衣

### D1. 完成人脸贴纸开关和权限生命周期

**依赖：** A2；使用现有 `feature-camera-fx` 架构。

接通通话 debug 菜单到 `CameraFxGrantedContent` 与 lab prefs；确保相机仅在用户主动打开并授权后绑定，关闭/离开页面立即停止采集。

**验收：** 首次拒绝、允许、撤销权限、关闭开关、后台/返回页面均通过设备验证；不开相机时不初始化相机分析；相机帧不上传、不持久化。

### D2. 手势识别与舞台 cue 原型

**依赖：** D1。

先在实验室用 Pose 骨架，再评估 Hand landmark / GestureRecognizer 和指尖 15–22；明确手势到既有 `emitStageGesture` / `cmp.cue` 的纯映射。手势冲突与误触时不持续触发特效。

**验收：** 真实设备上提供各手势的正样本、负样本、误触率和端到端帧率；单元验证纯映射；叠加层没有第二套 pointerInput 或事件总线。

### D3. 服装、帽子和头部替换的规格与素材验证

**依赖：** D1；依赖美术/授权素材，不依赖在线模型先行。

逐个变体在 `wardrobe-spec.json` 登记槽位、素材、参数来源、适用体型/姿态、遮挡关系与状态。在线试衣、帽子和头部替换分开验收，不以静态贴图效果推定头部替换已解决。

**验收：** 每个 active 变体有实际素材、设备截图/视频和参数来源；遮挡、旋转、光照/肤色边界、跟踪丢失恢复有记录；未知参数保持 pending；所有素材授权可追溯。

### D4. 相机/舞台效果交互验收

**依赖：** D1、D2；D3 的相应素材完成后才验试衣路径。

统一验证相机坐标、舞台归一化锚点、Lottie 时序和字幕/头像遮挡；相机贴纸默认本地锚定，只有用户操作才触发舞台效果。

**验收：** 低端与目标设备的帧率/温度可接受；跟踪丢失时效果平滑隐藏或恢复；权限、隐私提示与退出路径清楚；主通话不因相机效果掉音或崩溃。

## 阶段 E：开源项目与模型候选筛选

### E1. 候选清单与许可证/权利矩阵

**依赖：** 无；与 D1–D3 可并行。

逐项核查 `finger-frame-effect-ai`、IOPaint、LaMa、AnimeGANv3 ONNX 及实际依赖、权重和样例素材；记录维护状态、许可证、权重/数据条款、用途限制、署名/开源义务、隐私和内容风险。

**验收：** 每个候选有一手 LICENSE/model card/官方条款链接与核对日期；未读到关键条款标为阻塞；AGPL/GPL 或非商用条款按实际传播形态作合规评估，不把“实验 app”当豁免；无授权素材不进仓库。

### E2. IOPaint/LaMa 异物去除基准

**依赖：** E1 权利核验通过后才下载或运行模型；D3 提供经授权的测试图。

以 CPU 服务端作为基准，测冷启动、单张/批量耗时、内存、队列、质量和失败处理；定义图像上传、保留、删除与访问边界。先离线评估，不接生产用户照片。

**验收：** 固定数据集与遮罩、硬件和版本可复现；质量由人工盲评并报告伪影；达到预先约定的延迟/资源门槛；数据不被模型供应方或评测脚本额外留存。

### E3. AnimeGANv3 ONNX 端侧基准

**依赖：** E1 权利核验通过。

核查 ONNX 权重许可与输入输出规范，测 Android CPU/GPU/NNAPI 候选路径的速度、内存、耗电、画质和包体，不默认下载或捆绑权重。

**验收：** 在目标设备上报告冷/热推理延迟、帧率、内存和能耗；与基准图做质量对比；模型可关闭、按需加载，失败回退原图；所有模型和转换工具来源留档。

### E4. 手势/帧效果候选技术评估

**依赖：** E1、D2。

评估 `sophiamyang/finger-frame-effect-ai` 的项目许可证、权重/素材边界、依赖和维护状况；与本机 MediaPipe + 本地 asset 锚定的方案比较，不先引入第三方代码。

**验收：** 复现所需的最小合法样例；比较识别稳定性、交互延迟、设备负载和维护成本；给出 adopt / adapt design only / reject 的结论与证据。

### E5. 明确排除项

**Lada 去马赛克不进入主线。** 不开展技术集成或分发。任何重新评估都需另立任务，写明合法正当用途、权利和内容审核依据，并通过人工审查。

## 阶段 F：受控原型集成

### F1. 按通过项逐个集成

**依赖：** 对应 E 任务通过；D 线接口和隐私边界稳定。

一次只接入一个候选，使用可撤销分支/开关，限定可见范围；不得把多个模型与相机交互一起上线，确保质量或性能退化能定位。

**验收：** 依赖和模型来源完整；构建/运行证据齐全；CPU/内存/延迟/包体达到其评估任务门槛；卸载/关闭回退可用；权限和数据删除行为可验证。

## 阶段 G：集成门与交付收口

每一阶段结束做一次协调验收：

- 对照任务验收逐条给 PASS / FAIL / BLOCKED，并附证据位置。
- FAIL 与 BLOCKED 必须有责任线、下一步和依赖；不将其写成“基本完成”。
- 目标内未完成事项留在原任务，不偷渡为新需求，也不关闭任务；新增目标另建任务。
- 代码合并前检查许可证、素材来源、隐私影响、设备性能、回滚开关和文档。
- 生产网络/服务部署需要明确变更范围和回滚证据；路线图本身不授权生产变更。

## 风险与处理

| 风险 | 影响 | 处理方式 |
|---|---|---|
| 设计文档与当前部署/代码不一致 | 按旧设计重复做或误报已完成 | A 阶段从当前代码、配置和日志重新取证；旧文档标注日期与证据范围 |
| 首帧慢归因错到网络/协议 | 浪费时间且可能破坏已通过链路 | 按阶段时间戳拆分，协议通过项保持关闭，先定位 TTS/agent 阶段 |
| 第三方代码、模型权重、数据权利不一致 | 无法合法分发或商业使用 | 分开审许可证和权利；关键项未知则只做不含受限资产的设计研究 |
| 相机在用户未选择时开启或帧外传 | 隐私与信任受损 | 用户明确进入并授权；本地处理；关页停采；设备验证上传与落盘边界 |
| 贴纸 demo 被误认为可用试衣/换头 | 产品承诺超过能力 | 头部、帽子、服装分成独立变体与验收，规格状态保持真实 |
| 大方向并行导致 worker 目标扩散 | 长期遗留与无法收口 | 按本文任务编号派工，单任务一个结果/验证/阻塞清单，跨线事项另立 |
| 情感互动产生依赖、谄媚或未成年人风险 | 用户伤害与上线障碍 | 设计和评分卡设置拒绝门槛；主动性保持可关、硬频控；上线前法务复核 |

## 未决产品决策

这些问题不阻塞路线图编写，但相应任务开始前应在任务卡确认：

1. Her 教学 demo 的首要受众是内部研发/评审，还是对外展示用户？
2. 虚拟试衣的首个目标是本地贴合预览，还是服务端生成效果？两者的隐私、延迟和成本差异很大。
3. 首批 Android 性能验收设备与体验门槛由谁确定？
