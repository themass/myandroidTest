## 2. 消息：格式、样式、反复进出（重点）

你提到的「Huawei 花很大代价优化消息类型和格式、颜色样式、退了进进了退」——这一块的正确性有两个维度：
**渲染对不对**，以及**反复进出后是否一致**（数据没丢、没重复、没乱序、状态没串）。

### 2.1 消息类型矩阵（每种都要「发出去 → 立刻看 → 退出重进再看」）

| # | 类型 | 关键检查点 |
|---|---|---|
| M1 | 纯文本（短/长/超长 5000 字） | 换行、超长不截断、长按可复制 |
| M2 | Markdown：加粗/斜体/列表/引用/表格/代码块 | 表格不串行、代码块可横向滚动 |
| M3 | 公式：行内 `$…$`、独立 `$$…$$`、乱写的 `$` | 不把普通美元符号解析成公式；上下标正确 |
| M4 | 图片：单张（刚缩小过）/多张 2 张 / 4 张 / 9 张 / 超过 9 张 | 单图不占满屏；多图排列；点击进大图；长按菜单 |
| M5 | 语音：录音发送、播放中、播放完、波形长度与时长对应 | 时长显示、播放中的动画、没有录音权限时的提示 |
| M6 | 文件卡片 | 文件名/大小/类型色块；点击能打开 |
| M7 | 正在生成 / 流式中 / 已停止 / 重新回答 | 流式逐字追加不重复；点停止后不再追加 |
| M8 | 失败消息 + 重试 | 重试成功后占位不重复；重试失败仍有提示 |
| M9 | 多选、删除、编辑 | 批量删除后列表与本地库一致 |
| M10 | 语音输入（按住说话） | 按住时状态、松手后转写、识别为空时的提示 |

### 2.2 样式（截图基线）

- 用户气泡 / 助手气泡的背景、圆角、最大宽度、左右边距
- 时间、已读/已发送、错误态颜色
- 深色模式（系统切换深色后**退出重进**，颜色是否仍正确）
- 字体缩放：系统字体调到最大号，消息不重叠、不被裁切
- 横竖屏：旋转后消息位置与草稿输入是否保留

### 2.3 反复进出（T5，重点）

用脚本循环，每一步截图 + 抓一次日志，最后逐张比对：

| # | 场景 | 期望 |
|---|---|---|
| S1 | 发 5 条不同类型的消息 → 返回 → 再进对话（×5 次） | 消息数量、顺序、内容每次都一致 |
| S2 | 流式生成中点返回 → 再进 | 不重复、不丢、不再接着生成 |
| S3 | 生成中断网 → 恢复网络 → 重进 | 失败态保留，重试可用 |
| S4 | 杀进程（`am force-stop`）后重进 | 本地缓存与服务端历史合并后无重复 |
| S5 | 切后台 5 分钟再回来 | 不需要重新登录，消息不重新加载闪烁 |
| S6 | 多个会话之间来回切换（×10 次） | 会话不串、未读数正确 |
| S7 | 编辑图片 → 完成后立刻返回 → 重进 | 草稿/已发消息是编辑后的图（本轮修过 D1，要回归） |
| S8 | 语音播放中退出再进 | 不会有两个声音同时播 |

> 自动化：`scripts/devicetest/loop.py --rounds 5` 跑「进入 → 文本快照 + 截图 → 退出」×N，
> 比对各轮的消息文本序列（数量/顺序/内容），截图存到 `/tmp/devicetest-loop/`。
> 文本快照比截图可靠：未读小红点和时间会变，但消息序列不该变。

## 4. 拍照解题（现在可以端到端测）

服务端已配好：模型 `doubao-seed-2-1-lite-260915`，`maxBytes=5242880`，超时 60s。
本轮实测（直打接口）：正确题图 3/3 答对，单次 8–13s，非题目照片正确返回 `questionFound=false`。

| # | 场景 | 期望 |
|---|---|---|
| P1 | 清晰正对题目 | 四角微调 → 矫正 → 结果含题目/步骤/答案 |
| P2 | 斜拍（梯形） | 矫正后文字不歪，无大片背景 |
| P3 | 桌面/风景/人脸 | 端上提示「未检测到题目边缘」，或服务端 `40002` 回取景页 |
| P4 | 模糊/过暗 | 清晰度提示；选「仍然识别」仍可出结果 |
| P5 | 断网 | 提示网络异常，可重试，不崩溃 |
| P6 | 服务端未配模型 | `50002` → 「解题服务尚未配置好」，不重试风暴 |
| P7 | 连续识别（额度） | 免费用户第 11 次返回 `42901`；`quota.json` 显示剩余 |
| P8 | 同一 `clientRequestId` 重发 | 命中幂等缓存，不重复扣额度 |
| P9 | 一张图多道题 | 当前只展示第一题（已知），结果不串 |
| P10 | 4000×3000 大图 | 不 OOM，上传前压缩到限制内 |

> **注意力度的先后**：P3/P6/P7 验证的是错误码链路（本轮刚修过 errno 透传），P1/P2 验证的是端上检测，
> 两者失败原因完全不同，报告里要分开写。

## 6. 陪伴 / Agent / LiveKit / Memory / deerflow

**现在没有服务端**（见第 0 节）。所以这一节分两部分。

### 6.1 现在能测的（服务端缺失时的行为）

| # | 场景 | 期望 |
|---|---|---|
| C1 | 打开陪伴标签 | 不崩溃；给出「服务暂不可用」之类的提示，而不是空白或无限转圈 |
| C2 | 各子页面（角色列表 / 记忆 / 偏好 / 事件 / 收件箱） | 同上，每个页面都要有自己的提示，不能只有一个转圈 |
| C3 | 接口超时、返回非 JSON、返回 500 | 降级提示；不崩 |
| C4 | LiveKit：拿不到 token | 停在文字对话，不尝试连接空房间 |
| C5 | token 过期 | 重新申请或明确提示 |
| C6 | 未登录进入陪伴 | 引导登录，不能发请求 |
| C7 | 发布版本里抽屉是否还有「测试」分组和 AgentChat 入口 | **必须没有**（发布前逐项确认） |

> 这一节现在是**验收「缺功能时的表现」**，不是验收功能。

### 6.2 服务端就绪后要测的（先写清楚，等接口）

写在这里是为了让服务端实现有明确的验收口径。

| # | 场景 | 期望 |

| C11 | LiveKit 双人房间 | 能听到对方语音、延迟 < 500ms、断线重连 |
