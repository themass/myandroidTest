# chat 发送模型：去掉「发送队列」，永远即时发送（设计 20261126）

用户诉求（A43-1）：「不要"发送队列"了，消息就应该立刻发送，参考豆包，agent需要智能处理，如果内容已经生成回复就继续把前一条回复返回给app；如果agent还没有生成，就是立刻取消生成中的回复，然后把用户后面发的和前面一条放到一起给大模型去生成，整个message是干净的，根据message内容整体生成回复……应该会对上面的这些用户消息统一回复才对，这样才是一个真人的感觉。」

## 0. 现状：要拆的和本就复用的

上一轮 A40 刚建的服务端裁决管道**正是这个模型的地基**，拆的只是本地队列 UI：

- 现在（A36）：生成中点发送 → 文字进**本地 FIFO 队列**（`QueuedText` 徽标「N 条排队中」+ 展开后「立刻发出/打断重发/撤回」三按钮），本轮结束才续发。用户不满意：他的消息被 App 扣住了。
- A40 已合线：`POST /v1/sessions/{id}/submit` 对 mid-turn 提交**服务端单一裁决**，回执 `disposition` 四值（`queue.py:12-16`、`chat.py:229-235` 核实）：
  - `started`：锁空闲，直接开新回合；
  - `merged`：回合还在 pre-output（只想没说）、重跑预算内 → 原地取消+重跑，模型条件含全部 pending 用户消息，发 `turn.restarted`；
  - `steered`：已在输出、预算内 → 注入正在跑的回合；
  - `queued`：进服务端队列，当前回合结束后排空成一个新回合。
- 客户端锁扣（A40 已实现）：`noteCaughtTurn`/`takeCaughtTurn` 接住排空回合（新订阅，未来帧+snapshot，一个字不丢）；`ChatStreamEvent.Restarted` 清半截防重复。

## 1. 新模型：一条规则——**输入框点发送，永远走网络，永远不本地排队**

```
用户点发送
  ├─ 用户气泡立即上屏（id = clientMessageId，A40 不变量原样保留）
  └─ POST submit（不带任何"现在要不要插"的 UI 决策——决策权全部交给服务端裁决）

服务端裁决 → 客户端只做三件事：登记锁扣 / 清半截 / 继续流式
  started  → 新回合正常流式（与今天首条发送无异）
  merged   → 正在思考的那轮被原地取消；收到 turn.restarted；
             回复对「前面几条 pending 用户消息」整体生成     ← 「真人感」的来源
  queued   → 当前回复**不受打扰继续输出**；新消息在服务端排队，
             本轮收尾后 ReplyStreamer 自动接住新回合流式展示   ← A40 接住回合路径原样复用
  steered  → （默认不再出现，见 §2 决策）
```

用户体感对照：
- 发完第一条、agent 还在想（屏幕上没有回复文字）→ 发第二条：第一条的回复**静默作废**（本来就没什么可损失的），模型看到「第一条+第二条」，**统一生成一个回复**。两条用户消息都在，各自气泡都在（历史干净：中间没有半截回复）。
- 发完第一条、回复已经吐了一半 → 发第二条：当前回复**照常讲完**（不打断真人说话），第二条随后被回答。

## 2. 设计决策（20261126 用户参与拍板 + 协调会话裁决）

- **D1（用户拍板）：本地队列不退役，加开关**。设置项「生成中发消息」两态：
  - **即时发送（默认）**：`SendActions.sendText` 不进本地队列，永远直接 submit，由服务端裁决（§1 流程）。QueuedBadge 不显示。
  - **排队模式**：保留 A36/A40 现状——进本地 FIFO，徽标「N 条排队中」+「立刻发出/打断重发/撤回」。
  开关放 chat 会话设置，持久化 prefs；`ChatUiState.queued`/`QueuedText`/chatkit 组件全部保留，仅 sendText 入口按开关分流。陪伴页等调用方不变。
- **D2（协调会话裁决，依据见 §2.1）：服务端 output 阶段默认 queued，不默认 steer**。裁决优先级：pre_output 且重跑预算内 → **merged**（取消重跑、合并回答）；output 阶段 → **queued**（当前回复完整讲完，新消息排空成新回合）；`steered` 保留代码路径但默认不触发（留给未来显式「插话进本轮」能力，如开关/按键显式请求）。改动点 `service/turn/queue.py` 一处 + 服务端单测。

### 2.1 D2 的依据（20261126 搜证 + 「真人」推演）

- **豆包文本端**：无官方文档直接说明；旁证一致——停止/打断是**显式操作**（桌面端有「中止正在生成的回答」快捷键，实时语音走显式 `response.cancel` 协议事件），上游会话是单在飞（忙时 409）。没有发现任何「新消息隐式打断正在输出的回复」的产品行为。
- **ChatGPT**：官方方向是 **queue**——生成中发的消息变 composer 上方 pending card，本轮结束后续发；**Esc 才显式打断立即发**（Codex TUI `press esc to interrupt and send immediately` 即此模式）。
- **「steer（注入正在输出的回复）」是编码 agent 工具（Codex/超星智能体）的概念**——它们能按工具步注入是因为输出本来就是离散步；真人聊天不是。超星文档把两模式命名为 STEER（马上发）/FOLLOW_UP（等回复完），也是**用户显式选**，不是默认。
- **「真人」推演（用户诉求的本体）**：
  - 回复**还没开始输出**＝人还在「组织措辞、没开口」→ 新信息来了当然合并进去一起答（真人会撕掉没发出去的草稿重写）→ `merged`。
  - 回复**已经在输出**＝话已经说出口 → 真人不会被人插嘴就吞回去，会**把这句讲完**再回应新消息 → `queued`。
  - 真人不存在「边说边把后半句改写成新答案」的中间态 → `steered` 不做默认。
  - 用户原话「如果内容已经生成回复就继续把前一条回复返回给app」与 `queued` 精确对应；「立刻取消生成中的回复…放到一起给大模型」与 pre_output 的 `merged` 精确对应。
  - 补充（非本轮默认）：真人也会「察觉新消息让当前话变得多余」——那属于显式停止按钮（已有），不做隐式。

**开关语义（D1×D2 组合）**：即时模式走裁决（merged/queued）；排队模式走本地 FIFO 等续发；A40 的 promote/interrupt 按钮只在排队模式出现。两条路径共用同一 submit/disposition 管道。
- **D3 「统一回复」不需要客户端拼消息**：merged 重跑的模型条件天然含全部 pending 用户消息（服务端历史就是上下文）。客户端不合并气泡、不二次提交，历史里两条用户消息+一个整体回复——这已经是「message 干净」的形状。**不做**气泡合并（豆包也不合并）。
- **D4 取消乐观化（A43-3）**：点停止/打断 → 本地立刻收尾（气泡定格、发送键复位、**「已取消」即时可见**），`cancelTurn` 网络请求后台发、失败静默重试。现实现是等两端都停完才更新 UI，慢。落点 `ReplyStreamer.cancel`。
- **D5 排空自动化**：queued 回执 → `noteCaughtTurn`（A40 已有）→ 当前轮 `runTurn` 末尾自动接住。用户全程无感，没有徽标。

## 3. 风险与边界

- 连点滥用：每次提交都进裁决；服务端 `DRAIN_BATCH_SIZE=10`、重跑预算限制兜底——预算耗尽 merged 降级为 queued（当前回复讲完再答），可接受。
- merged 竞态：裁决瞬间回合恰好进入 output → 服务端按那一刻定夺，客户端锁扣（skip/expected turn id）已经能消化两种落点。
- 老服务端缺 disposition：A40 规则不变——按失败处理、文字回输入框，绝不静默吞输入。
- A40 装机验证（versionCode 74）与新模型不冲突：74 是带按钮的中间态，本设计合线后按钮消失、管道相同。
