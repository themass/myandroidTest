# 激励视频、VIP 兑换与留存设计（草案）

状态：待确认。确认后再实现服务端和客户端。

## 1. 现状

- 客户端：`AdmobRewardAds` 已接入激励视频；获得奖励后调用 `ScoreTask` → `/user/ads/score.json?score=30`。
- 服务端：`ADS_CLICK_SCORE = 30`，每次看广告加 30 分；`initUserVip1/2` 定时任务把分数满 2500 / 4500 的用户升到 VIP1 / VIP2 并扣分；`paidEndTime <= now` 时 `level` 归 0（`updateLevelPaid`）。
- 问题：`ads/score.json` 由客户端直接上报，**没有服务端验证**，任何人都能伪造请求加分。新规则上线前必须改掉。

## 2. 积分与 VIP 兑换规则（建议）

| 项目 | 建议 |
|---|---|
| 单位 | 1 张“观看券” = 1 次**服务端验证通过**的激励视频 |
| 兑换 | 3 张观看券 = 2 小时 VIP（示例，可调） |
| 叠加 | 新 VIP 时长叠加到 `max(now, paidEndTime) + 2h`，不会覆盖已有时长 |
| 每日上限 | 每天最多 10 张（即约 6 小时 VIP），防刷也防滥用 |
| 冷却 | 两次观看间隔 ≥ 60 秒 |
| 有效期 | 观看券 7 天过期（可选，避免无限囤积） |
| 与旧积分 | 旧 `score` 保留展示，不再新增；存量积分可按比例折成观看券（例如 30 分 = 1 张） |

**VIP 的落地方式**：兑换成功后设置 `level = 1` 并延长 `paidEndTime`。这样复用现有的 `updateLevelPaid` 定时任务，到期自动降级，不需要新的 VIP 状态机。

## 3. 服务端验证（必须）

- 使用 AdMob 的**服务端回调（SSV）**：广告播完后，Google 服务器会回调我们的接口，带签名参数。
- 接口校验签名（Google 公钥）、`user_id`、`reward_amount`、`transaction_id`，并检查 `transaction_id` 没有用过（防重放）。
- 校验通过后写入 `user_reward_ticket` 表（用户、交易号、时间、状态），客户端只负责展示。
- 客户端不再直接上报奖励。

新增表（草案）：

```sql
CREATE TABLE user_reward_ticket (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  user_name VARCHAR(64) NOT NULL,
  transaction_id VARCHAR(128) NOT NULL UNIQUE,
  created_at DATETIME NOT NULL,
  used TINYINT NOT NULL DEFAULT 0,
  expire_at DATETIME NOT NULL,
  KEY idx_user (user_name, used)
);
```

## 4. 接口（草案）

- `POST /api/user/reward/redeem.json`：用 3 张观看券兑换 2 小时 VIP（需登录）。返回新的 `paidEndTime`。
- `GET /api/user/reward/status.json`：返回可用观看券数、今日已看数、冷却剩余秒数、VIP 到期时间。
- AdMob SSV 回调接口：仅接收 Google 请求，不对外暴露给客户端。

客户端礼物图标点击后：先调 `status.json` 判断是否在冷却中，再弹激励视频；视频完成后刷新状态，攒够 3 张时显示“兑换 2 小时 VIP”按钮。

## 5. 风控

- 同一设备、同一 IP 的每日上限。
- 观看券发放与兑换都写流水，便于回查。
- 冷却时间和每日上限放在服务端配置，可以随时调，不用发版。

## 6. 合规与上架注意

- 奖励规则要在界面上说清楚：看一次广告得 1 张券，3 张券换 2 小时 VIP。广告是用户自愿观看的。
- 隐私政策要补充：广告 SDK 收集的数据、奖励记录的保存期限。
- Play Console 的数据安全表单要如实填写。
- 上架前以 Google Play 当前的广告政策和 VPN 政策为准。

## 7. 留存与停留时长：整体思路

### 7.1 先解决“外链”问题

Google Play 对“只是网页包装”的应用审核严格（最低功能要求）。建议：

- **功能做在原生页面里**：把现在 WebView 打开的内容（攻略、资讯、活动）改成原生列表页，内容由服务端 JSON 下发，App 里渲染。
- **必须打开外部网站时，用 Chrome Custom Tabs**：比 WebView 更安全，体验接近浏览器，也不会被当成网页套壳。
- 减少外链数量，优先做站内闭环。

### 7.2 让用户有理由每天打开

| 方向 | 具体做法 | 留存价值 |
|---|---|---|
| 连接质量面板 | 原生展示节点延迟历史、断线次数、本周用量 | 用户会主动看 |
| 原生测速 | 一键测速，结果可对比、可分享 | 高频、有用 |
| 每日签到 | 签到得观看券，连续 7 天额外奖励 | 每天一次打开 |
| 邀请好友 | 分享卡（已完成）带邀请码，双方各得 VIP 时长 | 带来新用户 |
| 泄露检测 | DNS 泄露、IP 检测、WebRTC 检测（原生实现） | 有安全价值，信任感强 |
| 应用分组 | 常用应用一键加入分应用代理的预设 | 降低使用门槛 |
| 智能选路 | 按延迟和历史稳定性自动推荐节点 | 体验好，减少手动切换 |
| 通知 | 断线自动重连提示、VIP 到期提醒、每周用量报告 | 把用户拉回来 |
| 桌面组件 | 连接状态 + 一键开关（Quick Tile 已有基础） | 减少打开步骤 |

### 7.3 指标

- 次日留存（D1）、第 7 日留存（D7）。
- 每次会话时长、每日打开次数。
- 观看券发放量、激励视频完成率、VIP 兑换率。
- 功能使用率：测速、泄露检测、分组、邀请。

### 7.4 原则

- 不做强制观看广告、不做误导性按钮、不做假倒计时。
- 奖励是可选的，免费用户也能完整使用核心功能。
- 每个功能都要有真实价值，不做“为了停留而停留”的设计。

## 8. 建议的实施顺序

1. 确认第 2 节的兑换规则和数值。
2. 服务端先做：SSV 回调、观看券表、兑换接口，并停用客户端直接加分的接口。
3. 客户端：礼物图标（已完成）接入 `status.json` 和兑换按钮。
4. 留存功能按 7.2 的优先级逐个做：连接质量面板、原生测速、签到、邀请。
5. 把 WebView 外链改成原生页面。
