### 构建版本对不上的地方（必须留痕）

装机包的 versionCode 对应 bump commit `3da59bc5`，但 §5 表里依赖的「四选项特效面板」（`47279b0f`）与「特效面板拆分」（`27f8afc9`）**都晚于** `3da59bc5`——所以**装机包没有那版特效面板**，设备上只有旧的「特效测试」单按钮（`DigitalHumanLabHost.kt` → `emitStageGesture("pat_head")`）。

更硬的证据在设备上（2026-11-28 01:5x 实测，`run-as … cat shared_prefs/companion_dh_watchdog.xml`）：

```xml
<string name="companion.dh.active_engine_disabled">LIVE2D</string>
```

而本仓库源码里这个 pref 的 key 是 **`companion.dh.quarantined_engine`**（`DhEngineWatchdog.kt:98`）。
`git log --all -S "active_engine_disabled"` **全历史零命中**——装机包的 watchdog 实现和仓库 tip 不是同一版。

两条后果，都已写进脚本：
1. **本文件所有真机数字代表 `3da59bc5` 附近那一版，不代表仓库 tip**（装机包的精确身份无法从本仓库坐实）。需要 tip 的数字，必须由协调会话从 `weifu-refactor` 最新 tip 现场装机后重跑（本会话不装机）。

## 3. 空闲态内存（应用前台，无形象舞台）——已实测，但被广告/WebView 污染

命令：`dumpsys meminfo com.openapi.ks.chat`（取数时前台 = `HomeActivity`）。

| 分项 | KB |
| --- | --- |
| **TOTAL PSS** | **328,839**（≈ 321 MB） |
| TOTAL RSS | 457,724 |
| TOTAL SWAP PSS | 134 |
| Graphics | 57,824 |
| Java Heap | 25,308 |
| Native Heap | 60,400 |
| Code | **139,468** |

> **污染警告（重要，别把 321 MB 当应用基线）**：取数时这个进程里挂着 `AdActivity` + `Chrome_InProcess` WebView（每线程 CPU 里有 `Chrome_IOThread`、`AdWorker(Active`）。Code 段在不同时刻从 40 MB 跳到 139 MB，就是 WebView/广告动态加载所致。**这个数字是「跑过广告的一整天的空闲值」，不是「刚进陪伴页的空闲值」**，不能直接做增量分母。干净的进场前后增量必须靠 §6 的 stage 窗口（进场前 reset 窗口 + 进场后窗口差分）。

| 项 | 值 |
| --- | --- |

| 卡顿帧 / 卡顿率 | 1,189 / **23.0%** |
| CPU 帧时间 P50/P90/P95/P99 | 9 / 27 / **42** / 69 ms |

> **两条口径限制**：
> 1. **累计、混合页面**——首页/聊天/WebView/广告全混在里面，不是「稳态对话场景」。23% 卡顿里有相当成分是广告加载，不能当成舞台回归。
> 2. **gfxinfo 不统计 GLSurfaceView 的帧**（口径依据是 Android 的实现：gfxinfo 统计的是应用 UI 线程经 Choreographer 提交的帧；Live2D/Duix/Tao 这些 native 引擎的 buffer 由独立 GL 线程直接提交给 SurfaceFlinger，不经这条路径）。所以「CPU 帧 P95 = 42 ms」对 native 舞台**不适用**——native 舞台帧时间要用 `dumpsys SurfaceFlinger --latency <layer>` + `top -H`，脚本里已实现（`sf_latency()` / `thread_cpu()`）。**注意：本会话没有实测到这条差异**——空闲态前台只有 HomeActivity，`--list` 里我们的包只有 3 个窗口层、没有 GL 层（见 raw），GL 层要进通话页才存在，见 §6。
> 空闲态的 SF 层与每线程 CPU 已作为「口径基线」记录（见 raw），但空闲态没有 GL 层可测。

## 5. 建议预算线（每条标清支撑数字）

基于以上实测。**设备是 Kirin 旗舰 / 11 GB RAM**，所以这是「高档机基线」，不是「中端机」——中端预算要按经验再放宽 1.3–1.8×，并另找中端实机验证（见 §6 末尾）。

| 指标 | 建议预算线（本档机） | 支撑数字 | 信心 |
| --- | --- | --- | --- |
| **形象进程内存增量** | Live2D 单形象 **≤ 90 MB PSS 增量**（含 mask buffer），全画幅特效再 +30 MB | §2 ATRI 两张贴图解码 = 80 MiB（4096²+2048² RGBA8888）；§3 空闲 Graphics 57.8 MB 说明 GPU 侧已有可观占用 | 贴图部分是**算出来的硬底**，可信；+30 MB 特效余量待 stage 实测校准 |
| **冷启动到首帧（Activity）** | 热启动 HomeActivity **≤ 1,000 ms**；冷启动待测 | §4 实测热启动 Home 802 ms | 热启动可信；**冷启动 BLOCKED** |
| **形象加载到可见** | Live2D **≤ 800 ms**（暂拟，待实测） | 无实测（BLOCKED）；按 §2 84 MB 贴图上传 + moc3 717 KB 估 | **低，待 §6 实测替换** |
| **帧时间 P50/P95（稳态对话，Compose 档）** | per-frame CPU **P50 ≤ 8 ms / P95 ≤ 16 ms**（120 Hz 半帧 / 60 Hz 满帧预算） | §4 GPU P50 4 / P95 7 ms 健康；CPU 混合场景偏高（23% 卡顿）需舞台干净窗口复核 | 中；GPU 侧稳，CPU 侧要 stage 差分复核 |
| **帧时间（native GL 档）** | 等效 **≥ 50 fps**（层帧间隔 ≤ 20 ms P95） | 无干净 GL 窗口实测（空闲无 GL 层）；口径已建（SurfaceFlinger --latency） | **低，BLOCKED** |
| **同屏特效并发** | 同时 ≤ **3 个 Lottie 实例**，全画幅特效同屏 ≤ 1 | §2 Lottie 资产：fx_connected 全画幅 1080×1920/7 层，其余 512²/1–3 层、KB 级矢量；并发成本在合成层不在体积 | 中；**实测并发上限 BLOCKED** |

> 反例校验：架构文档 §7 提到 AIRI 的 WebView 栈 RSS 1.7–2.2 GB。本表把 Live2D 单形象增量定在 ≤ 90 MB、空闲应用被广告污染到 ~320 MB——量级上确认「几十 MB 预算」只对自己的 native 档成立，WebView 档（dh-vrm/dh-spine）不能套这条线。

## 6. BLOCKED：缺什么、测不了什么

**根因**：设备是**共享**的——另一会话正在用陪伴聊天页取数。`stage`/`fxlab`/`coldstart` 模式会**动 UI**（进通话页、切引擎、点特效、`am start` 重启），一旦别人中途接手，窗口前后差分就废，得到的是垃圾数字。所以这些项**不抢窗口硬跑**，标 BLOCKED，脚本写好待协调会话在独占窗口跑。

| BLOCKED 项 | 缺什么 | 待跑命令（协调会话，独占窗口） |
| --- | --- | --- |
| 形象进程内存**增量**（进场前后 PSS） | 干净的进场前/后窗口（空闲值被广告污染） | `python3 scripts/perf/p03_budget.py stage --allow-touch` |
| 帧时间 P50/P95（稳态对话，分 SIMPLE / LayeredAvatar / LIVE2D） | 分场景干净窗口 + GL 层 | 同上 |
| native GL 档帧时间（SurfaceFlinger 层间隔） | 通话页里的 GLSurfaceView 层 | 同上（脚本 `sf_latency` 已在每个场景窗口内取） |
| 形象加载耗时 `live2d_load_ms` | 进入 LIVE2D 舞台 + poll `Live2dRuntime` 日志 | 同上 |
| 同屏特效并发（Lottie 实例数 + 回收成本） | 特效连发窗口 + gfxinfo 差分 | `stage`（通话页特效面板）或 `fxlab --allow-touch`（debug 抽屉「特效引擎对比」，离线不连服务端） |
| 冷启动 TTID（冷进程多轮） | `am start -W` 会重启应用 | `python3 scripts/perf/p03_budget.py coldstart --allow-touch --rounds 5` |
| **中端机**预算线 | 没有中端实机（当前只有 Kirin 旗舰） | 借中端机 + 同脚本；本文件数字是高档基线 |

跑之前必查（脚本已内置）：
1. `adb devices` 确认 serial = 2MH0224B20002068，且前台是 `com.openapi.ks.chat`（脚本会在前台不对时 die）。
2. `run-as … cat shared_prefs/companion_dh_watchdog.xml` —— **本次实测该文件已存在 `companion.dh.active_engine_disabled=LIVE2D`**（见 §0），说明 Live2D 当前被熔断隔离、会被静默降级成 SIMPLE。stage 取数前必须先在引擎菜单主动再选一次 Live2D 解除，否则 `live2d_load_ms` 和 LIVE2D 档的帧/内存全是 SIMPLE 的数字。

输出落在 `<outdir>/raw/`（每条命令原始输出）+ `measurements.json` + `report.md`。
