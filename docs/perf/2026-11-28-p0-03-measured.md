### 构建版本对不上的地方（必须留痕）

装机包的 versionCode 对应 bump commit `3da59bc5`，但 §5 表里依赖的「四选项特效面板」（`47279b0f`）与「特效面板拆分」（`27f8afc9`）**都晚于** `3da59bc5`——所以**装机包没有那版特效面板**，设备上只有旧的「特效测试」单按钮（`DigitalHumanLabHost.kt` → `emitStageGesture("pat_head")`）。

更硬的证据在设备上（2026-11-28 01:5x 实测，`run-as … cat shared_prefs/companion_dh_watchdog.xml`）：

```xml
<string name="companion.dh.active_engine_disabled">LIVE2D</string>
```

而本仓库源码里这个 pref 的 key 是 **`companion.dh.quarantined_engine`**（`DhEngineWatchdog.kt:98`）。
`git log --all -S "active_engine_disabled"` **全历史零命中**——装机包的 watchdog 实现和仓库 tip 不是同一版。

两条后果：
1. **本文件所有真机数字代表 `3da59bc5` 附近那一版，不代表仓库 tip**（装机包的精确身份无法从本仓库坐实）。需要 tip 的数字，必须由协调会话从 `weifu-refactor` 最新 tip 现场装机后重跑（本会话不装机）。
2. **那条 `active_engine_disabled` 是死数据，不构成降级**。我先曾据此推断「这台机 LIVE2D 被隔离、跑出来会是 SIMPLE」——**这个推断是错的，已被 §4b 实测否证**：LIVE2D 场景里出现了真的 GL `SurfaceView` 层（60.2 fps）、`GLThread` 占 32% CPU、`Live2dRuntime: model load on GL surface` 日志出现。装机包既不读这个 key（它读源码里的 `companion.dh.quarantined_engine`，盘上没有），点菜单的 `clear()` 也没能删掉它（跑完后它还在），所以它就是更早某版构建留下的残留。脚本仍保留「按内容判降级」的 NOTE，但那条 NOTE 在这台机上属于**误报**，别被它拦住。

命令：`dumpsys meminfo com.openapi.ks.chat`（取数时前台 = `HomeActivity`）。

| 分项 | KB |
| --- | --- |
| **TOTAL PSS** | **328,839**（≈ 321 MB） |
| TOTAL RSS | 457,724 |
| TOTAL SWAP PSS | 134 |
| Graphics | 57,824 |
| Java Heap | 25,308 |
| Native Heap | 60,400 |
| Code | **139,468** |

> **污染警告（重要，别把 321 MB 当应用基线）**：取数时这个进程里挂着 `AdActivity` + `Chrome_InProcess` WebView（每线程 CPU 里有 `Chrome_IOThread`、`AdWorker(Active`）。Code 段在不同时刻从 40 MB 跳到 139 MB，就是 WebView/广告动态加载所致。**这个数字是「跑过广告的一整天的空闲值」，不是「刚进陪伴页的空闲值」**，不能直接做增量分母。干净的进场前后增量必须靠 §6 的 stage 窗口（进场前 reset 窗口 + 进场后窗口差分）。

| 项 | 值 |
| --- | --- |

| 卡顿帧 / 卡顿率 | 1,189 / **23.0%** |
| CPU 帧时间 P50/P90/P95/P99 | 9 / 27 / **42** / 69 ms |

> **两条口径限制**：
> 1. **累计、混合页面**——首页/聊天/WebView/广告全混在里面，不是「稳态对话场景」。23% 卡顿里有相当成分是广告加载，不能当成舞台回归。
> 2. **gfxinfo 不统计 GLSurfaceView 的帧**（口径依据是 Android 的实现：gfxinfo 统计的是应用 UI 线程经 Choreographer 提交的帧；Live2D/Duix/Tao 这些 native 引擎的 buffer 由独立 GL 线程直接提交给 SurfaceFlinger，不经这条路径）。所以「CPU 帧 P95 = 42 ms」对 native 舞台**不适用**——native 舞台帧时间要用 `dumpsys SurfaceFlinger --latency <layer>` + `top -H`（脚本 `sf_latency()` / `thread_cpu()`）。**这条已在 §4b 实测坐实**：LIVE2D 场景出现独立 `SurfaceView` 层与 `GLThread`，其帧不在 gfxinfo 计数里。

## 4b. 形象舞台场景对比（独占窗口实测）——本节是预算表的主数据

**取数窗口 2026-11-28 01:55:42 → 02:00:20**，设备/构建同 §0（versionName 1.1.0.74 / versionCode 1001000074，装机 2026-11-27 22:44:54）。命令：`python3 scripts/perf/p03_budget.py stage --allow-touch --sample 12`。

基线 = `companion-chat-no-stage`（陪伴聊天页，无舞台），PSS 中位 323,534 KB。

| --- | --- | --- | --- | --- |

**特效连发**：`pat_head`（装机包那个「特效测试」按钮直接 fire）+ 挥手光弧 + 接通花瓣 + 滑动流光 全部命中。

> **场景数字怎么读（重要，别只看单个数）**：
> 1. **LIVE2D 的 CPU 帧时间反而最低**（P95 17 ms vs SIMPLE 26 ms），代价是**内存增量最大**（+214 MiB）。三档不是单调「越高级越贵」，而是**贵在不同资源上**：SIMPLE 烧 CPU，LIVE2D 烧内存。预算表必须按资源分开定线。
> 2. **`>16ms%` 这一列在本机全是 ~100%，不可用作判据**——屏幕支持 120 Hz（帧预算 8.3 ms），窗口内几乎所有帧都超 16 ms，所以 16 ms 线在这台机上没有区分度。要用 8 ms 线或 SurfaceFlinger 实测 fps。上表没列这列就是这个原因。
> 3. **无形象基线只有 28 帧**：聊天页静止不出帧，属正常，不是漏采。它的 PSS 中位是干净基线（比 §3 的空闲 321 MB 基本一致，说明广告 WebView 已常驻）。
> 4. **Lottie 特效增量≈0**（ΔPSS −1 KB、帧时间不变、GPU 不变）：特效是矢量 shape 合成、无位图，成本落在 RenderThread/GLThread 的 CPU%（+5 个百分点）而不是内存。**单次触发**已测；**同时并发多个**的上限仍未测（见 §6）。
> 5. 单轮采样（每场景一个窗口），没有多轮取方差。数字是单点，不是分布。

## 5. 建议预算线（每条标清支撑数字）

基于 §4b 的独占窗口实测。**设备是 Kirin 旗舰 / 11 GB RAM / 120 Hz**，所以这是「高档机基线」，不是「中端机」——中端预算要按经验再放宽 1.3–1.8×，并另找中端实机验证（见 §6 末尾）。

| 指标 | 建议预算线（本档机） | 支撑数字 | 信心 |
| --- | --- | --- | --- |
| **形象进程内存增量** | **LIVE2D ≤ 220 MiB**；SIMPLE ≤ 120 MiB；LayeredAvatar ≤ 100 MiB（按档分别定线，不是一个数） | §4b 实测 ΔPSS：LIVE2D **+214.3 MiB**、SIMPLE +113.4、LayeredAvatar +91.8。ATRI 贴图解码 80 MiB（§2）解释了 LIVE2D 的大头，其余是 native/Cubism 运行时与 GL buffer | **高（真机差分）**。留 ~6% 余量给 mask buffer 与场景波动 |
| **冷启动到首帧（Activity）** | 热启动 HomeActivity **≤ 1,000 ms**；冷启动仍待测 | §4 热启动 Home 802 ms | 热启动可信；**冷启动 BLOCKED** |
| **形象加载到可见** | Live2D（ATRI，4096² 贴图）**≤ 3,000 ms**；小贴图模型应 ≤ 1,000 ms | §4b 实测 **2,655 ms**（单轮） | 中：单点采样，无多轮方差；换小模型未测 |
| **帧时间 P50/P95（Compose 档）** | CPU **P95 ≤ 28 ms**（= 120 Hz 下 3 帧内）；GPU **P95 ≤ 16 ms** | §4b：LayeredAvatar CPU P95 22 / GPU 10；SIMPLE CPU P95 26 / GPU 15 | 中-高：单轮；SIMPLE 离线很近，**没有余量**，加特效或更复杂布局会顶穿 |
| **帧时间 P50/P95（native GL 档）** | CPU **P95 ≤ 20 ms** / GPU **P95 ≤ 8 ms**；**SurfaceFlinger 实测 ≥ 55 fps** | §4b：LIVE2D CPU P95 17 / GPU 7；GL 层帧间隔 P95 20.8 ms = 60.2 fps | **高（真机实测）**；这条是三档里最健康的 |
| **形象舞台 CPU 总占用** | 全进程 **≤ 150%**（≈1.5 核）；LIVE2D+特效实测 146% 已顶到线 | §4b 每线程合计：无舞台 14% → LIVE2D 128% → LIVE2D+特效 **146%** | **高**；中端机核少，这条最容易先破 |
| **同屏特效并发** | 单次触发已证廉价；**并发上限仍建议 ≤ 3 实例、全画幅 ≤ 1** | §4b 连发 4 个特效：ΔPSS −1 KB、帧时间不变，只加 RenderThread/GLThread CPU ~5 个百分点；§2 资产 fx_connected 全画幅 7 层，其余 512² | 中：**并发（同时多个）未测**，测的是连续单次触发 |
| **包体积 / 下载流量** | APK 内形象固定 **≤ 6 MiB**；引擎按首启下载：Live2D ≤ 35 MB / 单形象 ≤ 10 MB | §1 APK 内 live2d 仅 6.1 MiB；§2 设备上 live2d 合计 33.1、单形象 6.6–9.5 MiB | **高，已实测** |

> **修订记录（重要）**：本节 4 行原先写的是「Live2D ≤ 90 MB」——那是**按贴图解码算出来的下界**（80 MiB），实测 ΔPSS 是 **214 MiB**，低了一倍多。下界不是预算：**Cubism 运行时 + GL buffer + mask buffer 的量比我估的大**。预算线已按实测抬高。
>
> 反例校验：架构文档 §7 提到 AIRI 的 WebView 栈 RSS 1.7–2.2 GB。本表把 LIVE2D 单形象增量定在 ≤ 220 MiB、空闲应用 ~320 MB——量级上仍确认「几十~几百 MB 预算」只对自己的 native 档成立，WebView 档（dh-vrm/dh-spine）不能套这条线。

## 6. 还剩什么没测

舞台场景已在 §4b 独占窗口取到（窗口 01:55:42 → 02:00:20）。剩下的项**不是脚本缺失**，是要么需要再一次独占窗口、要么需要别的机器。

| 未测项 | 缺什么 | 待跑命令 |
| --- | --- | --- |
| 冷启动 TTID（冷进程多轮） | `am start -W` 会 force-stop 重启应用，怕撞协调会话排其它设备步骤 | `python3 scripts/perf/p03_budget.py coldstart --allow-touch --rounds 5` |
| **同时**并发多个特效的上限（不是连续触发） | stage 模式目前连发=一个接一个，没测同屏叠多个 | `stage` 里加同时触发，或 `fxlab --allow-touch`（debug 抽屉「特效引擎对比」，离线） |
| Duix / Tao 档的帧与内存 | 设备上资产在（343/551 MiB），但本轮窗口只覆盖 LayeredAvatar / SIMPLE / LIVE2D | `stage` 扩引擎项 |
| 多轮方差 | §4b 是**单轮**单点，没有分布 | 同命令多跑几轮取 P50/P95 的波动 |
| **中端机**预算线 | 没有中端实机（当前只有 Kirin 旗舰） | 借中端机 + 同脚本；本文件数字是高档基线 |

**本次取数在设备上留下的状态**（下个用设备的人要知道）：
- `shared_prefs/companion_dh_watchdog.xml` 里多出 **`companion.dh.active_engine=LIVE2D`** —— 进形象页写的脏标记，退出通话页没清掉。按 `DhEngineWatchdog.onColdStart` 逻辑，只有下次进程**非正常死**才会据此隔离 LIVE2D；用户主动结束（reason=USER_REQUESTED）不会。这不是我留的隔离，是个待清的 active 标记。
- `companion.dh_lab.xml` 的 `companion.dh_call_stage=LIVE2D` / `companion.dh_live2d_model=ATRI` **取数前后未变**（脚本没改引擎选择）。
- 通话页已 BACK 退出，前台回到 `HomeActivity`，设备已交还。

跑之前必查（脚本已内置）：
1. `adb devices` 确认 serial = 2MH0224B20002068，且前台是 `com.openapi.ks.chat`（脚本会在前台不对时 die）。
2. 若弹出 `HwResolverActivity`（系统 chooser）会挡住导航——本次实测遇到过一次，`input keyevent KEYCODE_BACK` 关掉即可。脚本现在会先探测通话入口在不在，不再依赖底部标签。

输出落在 `<outdir>/raw/`（每条命令原始输出）+ `measurements.json` + `report.md`。
