# 发送与回复的交互设计（占位逻辑）

## 1. 原来的问题

旧做法：用户发出后，列表里先插一条「占位」气泡，回复回来后用另一条消息**替换**它。问题：

| 现象 | 原因 |
|---|---|
| 回复到达时整条气泡闪一下、跳一下 | 替换时消息 id 从本地临时 id 变成服务端 id，列表把它当成「删一条、加一条」 |
| 看不到逐字输出 | 每来一段文字都重启一次滚动动画，动画互相打断；网络一次给一大段，界面就一次出现一大段 |
| 失败时空气泡留在那里或整条消失 | 占位与真实消息是两条，失败路径只处理了一种 |
| 用户往上翻历史时被强行拉回底部 | 每次内容变化都滚到底 |
| 不能中途停止 | 没有停止入口 |

## 2. 设计原则

1. **一条回复从头到尾只有一个气泡。** 它的身份（列表 key）在创建时确定，之后不变；服务端 id 只是它的一个属性。
2. **状态是连续的，不是替换。** 思考中 → 输出中 → 完成，是同一个气泡在变，不是换一个。
3. **显示节奏和网络节奏解耦。** 网络来多少先放缓冲，界面按固定节拍匀速放出；积压越多放得越快，流结束后加速收尾。
4. **滚动只跟随在底部的人。** 用户往上翻就不打扰，给一个「回到底部」按钮。
5. **任何时候都能停，停了不丢东西。** 已经显示和已经收到的内容都保留并保存。
6. **失败不留垃圾。** 一个字都没收到就撤掉气泡、用户消息标成可重试；收到了一部分就保留那部分。

## 3. 一条回复的状态

```
[用户点发送]
   │ 用户气泡立即出现（发送中），输入框清空，发送按钮变成「停止」
   ▼
思考中 ── 气泡里三个跳动的点；不显示 footer
   │ 收到第一段文字
   ▼
输出中 ── 文字按节拍逐字长出；末尾可有光标；不显示 footer
   │
   ├─ 正常结束 → 完成：气泡定型，footer 出现，停止按钮变回发送；用户气泡标「已发送」
   ├─ 用户点停止 → 已停止：保留已有内容（含缓冲里还没放出的），保存；footer 出现
   ├─ 出错且已有内容 → 保留内容，用户气泡标「失败，点击重试」
   ├─ 出错且没有内容 → 撤掉气泡，用户气泡标「失败，点击重试」，顶部轻提示
   └─ 正常结束但全文为空 → 同上一条（不保存空回复）
```

## 4. 细节规则

| 场景 | 规则 |
|---|---|
| 节拍 | 每 40ms 放一次；一次放 `积压/8` 个字，最少 1、最多 48；流结束后一次至少放 `积压/3`；不切断 emoji 等代理对 |
| 滚动 | 用户停止滑动时，在底部就「跟随」，不在底部就「不跟随」；内容增长本身不改变跟随状态；跟随时无动画贴底；自己发的消息一定滚到底 |
| 回到底部 | 不跟随且列表非空时，底部中间出现圆形向下按钮；点击后动画滚到底并恢复跟随 |
| 停止按钮 | 只在输出期间出现，替换发送按钮；语音模式下不显示 |
| 重复发送 | 回复输出期间不能再发送（发送按钮是停止按钮） |
| 重新生成 | 在最新一条回复上；用同一个用户问题重新请求，旧回复被新回复替换（同一个位置、同样的生命周期） |
| 编辑用户消息 | 输入框上方出现「编辑消息」条；发送时替换该用户消息，删掉它之后的所有消息，再请求新回复；点 × 取消编辑 |
| 附件消息 | 图片/文件和文字是同一条用户消息；助手回复走同样的生命周期 |
| 离开页面再回来 | 已完成和已停止的回复从本地读出；正在输出的回复如果中断，按「出错且已有内容」处理 |

## 5. 和豆包、微信的对照

- 豆包：发送后立即出现思考态，逐字输出，输出中底部有停止按钮，完成后在最新回复上出现操作栏——本设计与之一致。
- 微信：不是生成式对话，不适用。
- ChatGPT 类产品的「编辑后截断后续对话」被本设计采用（用户已确认）。

## 6. 依赖服务端的部分

- 逐字效果的前提是服务端真的逐段返回（SSE 每段 `data:` 立即 flush）。如果网关或服务端整体缓冲，客户端只能平滑地「吐」出一大段，开始时间会推迟。需要在真实网络下抓一次响应确认。
- 服务端有时返回空回复，原因未查明。客户端按「全文为空」处理，不保存。

## 6. 与代码的差异（截至 2026-11-08）

以下是设计与当前代码不一致或尚未实现的部分，按影响排序：

1. **「已发送」标签没有显示。** 设计里用户气泡在完成后标「已发送」；代码只在 `DeliveryStatus.FAILED` 时显示红色感叹号和重试入口，成功状态没有文字标签。
2. **重新生成不是原位替换。** 设计要求新回复替换旧回复（同一位置、同样的生命周期）；代码 `ChatViewModel.onRegenerate` 先删掉最后一条用户消息之后的所有消息，再重新请求，新回复出现在列表末尾。
3. **离开页面再回来时中断的回复没有处理。** 设计要求正在输出的回复中断后按「出错且已有内容」保留；代码从本地库和服务端历史重新加载，中断的回复没有单独的恢复逻辑，未经验证。
4. **失败时的「顶部轻提示」**：设计要求顶部轻提示；代码通过 `ChatUiState.error` 传递文字，展示位置由 UI 决定，未确认是否就是顶部提示。
5. **附件消息的失败文案**：设计写「失败，点击重试」；代码的失败入口是感叹号图标，文字提示只在出错时通过 `error` 显示。
6. **停止按钮**：设计要求停止后 footer 出现、已缓冲的内容保留；代码 `finishStopped` 保留缓冲内容并保存，footer 在 `streaming` 结束后显示，符合设计，但未在设备上验证（模拟器无法启动）。
7. **节拍与滚动**：`REVEAL_TICK_MS = 40`、积压除以 8（最多 48）、结束时至少除以 3，与设计一致。滚动跟随规则在 `ChatMessageList` 中实现，与设计一致。
8. **空回复**：设计要求「全文为空」撤掉气泡并提示；代码已在 `ChatViewModel` 处理，提示文字为「没有收到回复，请重试」。

以上差异中，1、2 会直接影响用户看到的效果，建议优先处理。
